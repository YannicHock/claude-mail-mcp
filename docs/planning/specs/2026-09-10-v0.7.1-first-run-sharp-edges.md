# v0.7.1 — First-run sharp edges — design

Status: drafted 2026-09-10, pending owner review.

Covers the whole v0.7.1 milestone: what an instance does when a mailbox's credentials
are wrong, and the duplication that made every such fix touch two files at once.

Companion to `2026-09-10-issue-126-shared-modules.md`, which carries wave 0 on its own
because it is the only item here that changes how the images are built.

Issues: #126 (+#132 closed by it), #146, #147, #130, #137, #127, #139, #128, #134,
#148, #136, plus two new provider issues created with this spec.

## 0. Problem

The README's first line says this connector exists *because every other Claude email
connector targets Gmail*. The first real multi-account deployment, on 2026-09-10,
failed on Gmail.

The account was added through the settings UI. Autoconfig worked — the log shows
`add mailbox looked up an address found:true`, so hosts, ports and TLS came back
right. What failed was the password: Google accepts only an app password over IMAP
once 2-step verification is on. Three separate defects then compounded:

1. The mailbox was **stored anyway**. `POST /settings/mailboxes` never calls
   `probeAccount`; the connection test is a button beside Save, not a gate in front
   of it.
2. Every later tool call returned **`Command failed`** and nothing else.
   `src/probe.ts` has told a rejected password apart from an unreachable host since
   #3, but that classifier is private to the probe and the MCP tools never see it.
3. **The log said nothing.** `src/tools-mail.ts` carries a bare `catch {`. An
   operator following the obvious advice — check the server log — found no trace of
   a failure that had just happened.

None of this blocks a running instance. All of it costs an operator time, and the
third costs them trust: a service that fails silently is a service you stop believing.

Underneath sits a fourth problem that is the reason the first three are awkward to
fix. Six modules are mirrored across the two packages — about 1,650 lines of source
and 530 lines of test — because the packages have separate Docker build contexts and
cannot import from one another. The wire contract these fixes must extend,
`settings-api.ts`, is one of them, and it is the largest: 1,058 lines in each package,
not the 581 issue #126 records. It has nearly doubled since that review.

## 1. Scope

**In:** classifying and reporting credential rejection everywhere it can happen;
making the save path probe before it writes; telling an operator what their specific
provider requires; and consolidating the mirrored modules so the wire contract has
one home.

**Out:** OAuth-based mailbox authentication. That is what Outlook and Gmail-for-
Workspace actually want, it is a v0.9-shaped change to how accounts are stored and
refreshed, and nothing in this milestone should pretend otherwise. v0.7.1 tells an
operator that a provider needs an app password, or that it cannot be served at all;
it does not learn a second authentication scheme.

**Out:** the remaining review findings — #129, #131, #133, #135, #138 — and the older
duplication issues #6, #8, #72, #75. They stay in the backlog. The cut line for this
milestone was *code the Gmail chain opens anyway*, plus the two P1 security strands.

## 2. Version

This releases as **0.7.1**, not 0.8.0, even though §5 changes the behaviour of an
existing route: a save that used to succeed now refuses.

The reason is not SemVer purity. In this repository the version numbers *are* the
roadmap — `v0.8` is a milestone already named and populated ("Mail depth": #27, #28,
#29). Renumbering this release would collide with a plan rather than describe a
change. The behaviour change is real and belongs in a CHANGELOG entry that names it,
under a heading an upgrading operator will read.

The shipped `docker-compose.yml` pulls `ghcr.io/yannichock/...:latest` and does not
build, so #126's build-context rework reaches CI and anyone building by hand — not an
operator upgrading.

## 3. Shape of the milestone

Three waves. The ordering is forced, not stylistic: wave 1 and wave 2 both extend
`settings-api.ts`, and wave 0 is what decides whether that file exists once or twice.

```
wave 0   #126  shared/ consolidation                      (closes #132)
           │
           ▼
wave 1   #146 → #147 → #130 → #137 → #127 → #139 → #128 → #134
           │
           ▼
wave 2   #148 → provider research → unsupported-at-lookup

parallel #136  /authorize redirects into the header set
```

**#126 goes first.** Doing it last would mean every `settings-api.ts` change in waves
1 and 2 is made twice and re-pinned by a drift test that #126 then deletes. Doing it
first means the wire contract is edited once, at its final address, and #134 can put
the timeout budgets straight where they belong. The cost is that the riskiest change
in the milestone runs while nothing else is half-finished — which is also an argument
for it going first.

**Wave 1 is serial, not parallel.** Six of its eight issues touch
`src/settings-routes.ts` or `oauth/src/setup-routes.ts`. Splitting them across
concurrent branches produces conflicts in exactly the files being restructured. Run
them in one lane, in the order above, each as its own commit.

**#136 is genuinely parallel.** It touches `oauth/src/authorize*` and nothing any
other issue opens. It can run alongside any wave.

**The one guaranteed conflict is `CHANGELOG.md`.** Every issue adds an entry. If any
of this is ever split across concurrent branches, that is the file that will collide.

## 4. Wave 1 — the credential chain

### 4.1 #146 — the classifier reaches the tools

`isCredentialRejection` in `src/probe.ts` reads imapflow's `authenticationFailed`
together with a real `NO`/`BAD`, or RFC 5530's `AUTHENTICATIONFAILED` response code.
It moves to the shared module beside the timeout helper — **moves**, not copies. A
test fails if a second implementation appears, the way the mirrored modules are
pinned today.

`src/tools-mail.ts` and `src/tools-calendar.ts` then report the classified reason:
*"the server rejected these credentials"* rather than `Command failed`, naming the
account id, because a multi-account instance must say **which** mailbox.

Each such failure leaves exactly one `warn` line carrying the account id and the
classified reason. Never the password. Never the raw server line if it can echo one —
`MAX_MESSAGE_LENGTH` and `describe()` in `probe.ts` are the existing precedent and
the new logging uses them.

A genuinely unreachable host still reads as a connectivity failure, in both the tool
answer and the log. That distinction is the whole point; a classifier that collapses
it is worse than none.

### 4.2 #147 — the save path probes

`POST /settings/mailboxes` and `POST /settings/mailboxes/:id` run `probeAccount`
before writing.

| outcome | result |
| --- | --- |
| IMAP or SMTP rejected | **write refused**, page returns showing per-service what happened |
| CalDAV failed | **write proceeds**, failure shown |
| operator clicked *Save anyway* | write proceeds, nothing probed |

CalDAV does not gate a save because it fails for benign reasons far too often and is
optional by design. Showing it is right; refusing on it is not.

*Save anyway* is a second, distinct button. It is never the default and **never
reachable by pressing Enter** — #140 is the reason that constraint is written down
rather than assumed. It exists because a server in maintenance, a network blip, or an
operator who knows better should not be stuck behind a probe.

The override travels as a documented field in the shared wire contract, so the wizard
can express *"the operator clicked Save anyway"* rather than the two paths disagreeing
about what a save means.

The rule then lives in the connector, in one place. **The wizard stops enforcing it
in the OAuth layer** — today it calls `test`, reads the result, and only then calls
`create`, which puts the rule in the caller rather than in the thing being protected.
From the operator's side the wizard behaves exactly as it does now.

### 4.3 The four findings inside those routes

These are not a separate project. They are what the code looks like when you open it.

- **#130** — `rejected()` is a closure inside `POST /settings/mailboxes:484-500`, and
  the very next route writes the same JSON-vs-HTML fork out longhand, five-line
  preamble included. Hoist it to a module-level helper both routes use.
- **#137** — `express.json({ limit: "5mb" })` is mounted app-wide at `src/app.ts:140`,
  ahead of the settings router. body-parser sets `req._body`, so the settings
  router's own 64 KB `jsonBody` is **dead code**: the JSON branch accepts 5 MB where
  the form branch of the same route refuses at 64 KB. Since #147 extends that JSON
  surface, the limit has to be true before the field is added to it.
- **#127** — four bare `res.redirect(303, …)` at `:529`, `:696`, `:776`, `:814` carry
  none of `SETTINGS_HEADERS`, while every other send site in the file goes through a
  helper that sets them. Three of the four are in the create/update paths #147
  rewrites. Add `sendRedirect` beside the three existing helpers, and one test case
  that follows a POST with `redirect: "manual"` and asserts the full set on the 303 —
  `settings-headers.test.ts` exists to stop this set drifting and currently never
  asserts on a redirect.
- **#139** — the wizard emits `<input type="hidden" name="default" value="1">` with
  no way to untick it, `AccountsStore.create` appends unchanged, and step 2 is
  re-enterable. A second mailbox is therefore stored as a second default:
  `resolveAccount` silently picks whichever comes first, `publicSummaries` reports
  both, and the *Make default* button on the first appears to do nothing. Clear the
  flag on the other accounts inside `create`/`update` — that is the one place that
  already knows the whole list, and it fixes the wizard and the settings form at
  once. Whether a *later* wizard mailbox should default at all is a question for the
  screen, decided separately and after.

### 4.4 #128 and #134 — the wizard's two leftovers

**#128** — `carrying()` at `oauth/src/setup-routes.ts:1097` and `withSharedPassword()`
at `:1127` encode the identical rule twenty lines apart, differing only in
`Record<string, string>` vs `Record<string, unknown>`. `carrying`'s own doc comment
says so. The subtle half is the CalDAV clause — spread the shared password onto
`caldavPass` **only** when `caldavUrl` is non-empty, because a block that is nothing
but a password probes a server that was never named. That clause is currently stated
twice. One generic `spreadSharedPassword` through `stringField` removes about twenty
lines and leaves one rule.

**#134** — two wizard budgets must stay above the connector's own, or the wizard
gives up on work that is still running:

| wizard | connector | must be |
| --- | --- | --- |
| `setup-routes.ts:1190` `PROBE_TIMEOUT_MS = 30_000` | `probe.ts:22` `TOTAL_TIMEOUT_MS = 25_000` | wizard > connector |
| `setup-routes.ts:1215` `LOOKUP_TIMEOUT_MS = 13_000` | `autoconfig.ts:74` `AUTOCONFIG_TOTAL_TIMEOUT_MS = 10_000` | wizard > connector |

Three comments state it correctly and nothing checks it. Raise the connector's probe
budget to 40 s and the wizard silently gives up at 30, showing *"the connector did not
answer"* for a probe that was working — the exact class of failure #82 was filed
about. The budgets move into the shared wire-contract module, the connector uses them
as its defaults, and the wizard derives its two as `budget + slack`. The relationship
becomes arithmetic instead of a comment.

This is the clearest single argument for #126 going first: after the consolidation
there is one file to put them in, and it is already the thing both packages import.

## 5. Wave 2 — the providers

`src/providers.ts` holds eight entries since #70 — mailbox.org, Fastmail, iCloud,
Migadu, Posteo, Hetzner, mailcow, iRedMail. **Gmail is not among them**, and would
not have helped if it were: the table carries connection settings, and the connection
settings were never the problem.

### 5.1 #148 — the note, and only on rejection

An optional `credentialNote` on a provider entry: data, not logic. It renders in
exactly one situation — **a probe reported a credential rejection and the address's
domain matches an entry that has one.**

Not on the form. Eighteen fields do not need advice for a problem most operators do
not have. On a rejection it is targeted: the operator has just been told the server
refused their password, and the next sentence says why that happens here.

Never on a connectivity failure. That is the distinction #146 exists to draw, and
rendering the note on the wrong side of it would undo the point.

Gmail's note is the three things that go wrong, in the order they go wrong:

- 2-step verification means IMAP takes an **app password**, created at
  `myaccount.google.com` → Security → App passwords
- Google shows it as four groups of four characters; paste it **without the spaces**
- on older accounts, IMAP access can still be switched off in Gmail's own settings

Adding a provider without a note stays valid — the field is optional.

### 5.2 The research pass and `docs/PROVIDERS.md` (new issue)

The same discipline #70 applied to hosts and ports, applied to what each provider
wants from a password: only what is verifiable against that provider's own current
documentation, every claim carrying the source URL it was checked against, and
omission rather than a guess.

It produces three kinds of answer, and the third is why this is not just a data entry
task:

| kind | who | becomes |
| --- | --- | --- |
| needs an app password **when 2FA is on** | Gmail, Yahoo/AOL, Zoho, mailbox.org | `credentialNote` |
| needs an app password **always** | Fastmail, iCloud | `credentialNote` — both already in the table, both currently incomplete |
| **cannot be served at all** | Outlook.com / Microsoft 365, Proton | §5.3 |

Fastmail and iCloud are the reason this is a pass over the whole table rather than a
Gmail entry. Both are already shipped, both are named in the README's opening
sentence, and for both the account password over IMAP is hopeless regardless of 2FA.
The table has been silently incomplete about its own flagship providers.

The report is `docs/PROVIDERS.md`: which providers this connector serves, what each
needs from a password, which it cannot serve and why, every entry sourced. The table
values are its by-product. `DEPLOYMENT.md:1249` currently mentions app-specific
passwords for Gmail, iCloud and Fastmail in passing, inside a section about revoking
them — it stops carrying that knowledge alone and points here.

### 5.3 Unsupported providers, named before the password (new issue)

Microsoft retired IMAP basic auth; Proton requires the Bridge. Neither will ever
answer a username and password from this connector, and someone who types an
`@outlook.com` address lands in exactly the Gmail scenario with no way out of it.

An `unsupported` entry in the provider table, rendered **at address lookup — before
any password is typed.** The wizard already looks the address up first
(`add mailbox looked up an address found:true` appears in the #146 log before
anything else), so the moment exists and costs nothing to use. Nobody should type a
password for something that cannot work.

This is a different render site and a different moment from §5.1, which is why it is
its own issue rather than another field on the same one.

## 6. Acceptance

Every issue carries its own criteria; those stand. The milestone additionally closes
only when the case that opened it is verified **on the live Hetzner instance**, not in
the suite:

1. A Gmail mailbox added with a real Google app password saves, and `list_folders`
   answers.
2. The same mailbox with the plain account password is **refused at save time**, the
   response naming IMAP as the service that rejected it, with the Gmail note visible.
3. The connector log carries one `warn` line for that rejection, with the account id,
   and no password anywhere in it.
4. An `@outlook.com` address is called out at lookup, before a password field is
   filled.
5. The two other accounts on that instance are untouched, and exactly one of the
   three is default.

Tests would not have found this case — the deployment did. The milestone ends where
the deployment says it does.
