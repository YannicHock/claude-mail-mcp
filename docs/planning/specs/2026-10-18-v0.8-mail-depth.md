# v0.8 — Mail depth — design

Status: **approved 2026-10-18.** The owner decided §2 (table at the top of §2). Every
recommendation was taken except §2.6, which became configurable, and §2.14 (#247) was added.
Sections 3–8 hold as written; where §2.6 or §2.14 changes them, the decision says how.

Covers the whole v0.8 milestone. Its description says what it is for: "The two things still
missing from the mail surface, plus invitations", and "the last milestone that adds mail
capability. After it the surface is what 1.0 ships."

Issues: #27 (`list_threads`), #28 (incoming attachments), #29 (calendar invitations over iMIP,
including the REPLY that answers one), #162 (a later wizard mailbox silently takes over as
default), #182 (three hand-maintained provider lists); the defects of §9 as #239 (F1), #240 (F2),
#241 (F3) and #242 (F4 + F5); and #247 (an `http://` CalDAV URL sends credentials in
cleartext, §2.14).

Implementation plan: `docs/planning/plans/2026-10-18-v0.8-mail-depth.md`.

## 0. Problem

Claude can list, search, read and send mail, but it reads one message at a time and stops at
the attachment list. A conversation of eight replies costs eight `get_message` calls, and
Claude rebuilds the thread itself (#27). It can see that a PDF is attached and cannot open it
(#28). On the calendar side, v0.7.4 made the calendar server's own mail an explicit choice
(`notify_attendees`), but the connector itself still sends no invitation, and nobody can
answer one (#29). On a calendar server that does not schedule (Radicale), `notify_attendees:
true` today tells no one at all.

#162 and #182 are small, older issues from the settings work that ride here because they
belong to no other milestone.

### 0.1 What was measured (2026-10-18)

Everything below was run against the pinned fixtures from `docker-compose.test.yml`, started
as separate containers on host ports 13143/13025 (GreenMail 2.1.13) and 15232 (Radicale
3.8.1) so that other checkouts' runs on 3143/3025/5232 were not disturbed, and stopped
afterwards. The probes were throwaway scripts using the repository's own `imapflow` 2.0.0,
`nodemailer` 10.0.1 and `mailparser`.

| M11 | Radicale `OPTIONS` | `DAV: 1, 2, 3, calendar-access, addressbook, extended-mkcol`. **No `calendar-auto-schedule`.** `schedule-outbox-URL` and `schedule-inbox-URL`: 404. Radicale does not schedule, so no one is mailed by it, ever. |

What was read, not run:
- **The MCP spec, revision 2025-11-25** (the SDK 1.30.0 in `package.json` speaks it). A tool
  result's `content` may hold `text`, `image` (`data` base64 + `mimeType`), `audio`,
  `resource_link` (a URI the client may fetch) and an embedded `resource` (`uri`,
  `mimeType`, and `text` or `blob` base64), each with optional `annotations` (`audience`,
  `priority`). `structuredContent` with an `outputSchema` is separate, and SHOULD be
  repeated as a text block.
- **imapflow 2.0.0** has no `thread()` call. `THREAD` would go through the low-level `exec`.
  It does have `download(range, part)`, which decodes a part and converts text to UTF-8, and
  `threadId` for servers with `OBJECTID` or `X-GM-EXT-1`.
- **Server capabilities, from documentation, not from a login** (no real account was
  touched). Gmail advertises `X-GM-EXT-1` (Google's IMAP extensions page) and no `THREAD`.
  Dovecot advertises `THREAD=REFERENCES THREAD=REFS THREAD=ORDEREDSUBJECT` by default, and
  mailbox.org, Posteo, mailcow, iRedMail and Hetzner's hosting run Dovecot. Cyrus (Fastmail)
  implements `THREAD=REFERENCES`. iCloud and Migadu are unknown. None of this changes the
  recommendation in §2.1; it is why option B would help most providers and not Gmail.
- **Nextcloud (Sabre).** Its scheduling plugin adds `calendar-auto-schedule` to the `DAV:`
  header (RFC 6638 §2), which is what §2.8's detection relies on. Its iTIP broker is meant
  to send no REPLY for an attendee copy whose `ORGANIZER` carries `SCHEDULE-AGENT=CLIENT`
  (RFC 6638 §7.1). Both are acceptance's to confirm (A9, A10).
- **The MCP endpoint's own request limit** is 5 MB (`src/app.ts:155`,
  `express.json({ limit: "5mb" })`). A `send_message` whose attachments arrive as base64 in
  the request therefore cannot carry more than about 3.7 MB of file. §2.7 matters because of
  this.

## 1. Scope

**In:**
- `list_threads` and `get_thread` (#27).
- `get_attachment`, and forwarding an attachment by reference (#28).
- iMIP: invitations, updates and cancellations the connector sends itself where the calendar
  server does not, and answering an invitation (#29).
- An invitation in a received message is reported by `get_message` (#29, the reading half).
- #162: the wizard stops making a later mailbox the default.
- #182: one provider registry, with the documentation table pinned by a test.
- #247: an `http://` CalDAV URL is refused for a host that is not local (§2.14).
- The mail defects found while writing this (F1–F5, §9): F1–F4 sit on the paths #27 and #28
  build on, and F5 is one line in a file that PR is already changing.

**Out, explicitly:**
- **Folder management and flags/stars.** The milestone description rules them out.
- **PDF text extraction in the connector** (§2.5, option C). Claude reads PDFs itself when it
  receives them; if acceptance A5 shows the claude.ai client does not pass them on, this
  comes back as its own issue.
- **Sending an invitation from a mailbox with no calendar** (§2.11). Without a stored event,
  an invitation could never be updated or cancelled.
- **Processing incoming iMIP automatically** (a REPLY that updates the organizer's copy, a
  CANCEL that deletes it). The connector reads such mail when asked, and changes nothing on
  its own.
- **Counter-proposals and delegation** (`METHOD:COUNTER`, `DELEGATED-TO`). RFC 5546 has them;
  no one has asked.
- **Threads across all folders** (Gmail's "All Mail" view). §2.2 takes one folder plus Sent.
- **The JSON `/settings/mailboxes/test` answer that drops the credential note**, and the
  `refusalNotice`/`credentialAdvice` merge (#182 §4, last two bullets). They are a separate,
  already-filed seam, and touch the settings routes, not the tables.
- **The calendar module split** (#234, v0.7.5). This milestone is planned against its result.

### 2.1 Where a thread is computed (#27)

- **A — In the connector, always (recommended).** Fetch the envelope, `Message-ID`,
  `In-Reply-To` and `References` of the newest *N* messages of the folder (§2.2), and group
  them with RFC 5256's `REFERENCES` algorithm (JWZ's, without the subject merge step: two
  messages with the same subject and no shared reference are two threads). One
  implementation, the same answer on every server, and fully testable against GreenMail,
  which has no `THREAD` (M1).
- **B — The server's `THREAD=REFERENCES` where advertised, the connector's fallback
  elsewhere.** The server sees the whole folder, not a window. But it is two implementations
  whose answers differ in edge cases (the server merges by subject), the server path cannot
  run against GreenMail (M1), and it needs imapflow's undocumented `exec`. Gmail has no
  `THREAD` anyway.
- **C — B, plus Gmail's `X-GM-THRID`.** Gmail's own grouping, which matches what the Gmail UI
  shows. A third implementation, and Gmail-only.

  A's window is its weakness: a reply whose parent is older than the window starts its own
  thread. The answer says so per thread (`complete: false` when a `References` entry was not
  found in the window), so Claude can widen the window or search.

### 2.2 What one thread spans (#27)

- **A — The named folder only.** Simple, and one-sided: in INBOX, every thread lacks the
  user's own replies.
- **B — The named folder plus the account's Sent folder (recommended).** Sent is the folder
  the account already knows (`mail.sentFolder`). Messages are merged by `Message-ID`, so a
  message in both is counted once. `include_sent: false` turns it off; with no Sent folder
  configured it is off, and the answer says so. This depends on defect F1 being fixed:
  today a Sent copy carries a different `Message-ID` from the message that went out, so a
  reply to it would never join the copy.
- **C — Every folder.** Expensive on a large account (a fetch per folder), and the
  connector has no index to make it cheap.

  **The window**, whichever is chosen: `limit` messages per folder, default 100, at most
  500. One `FETCH` of envelopes and three headers per folder, never bodies.

### 2.3 What `list_threads` answers, and whether `get_thread` exists (#27)

- **A — `list_threads` returns message references, and a new `get_thread` returns the
  messages (recommended).**
  - `list_threads(mailbox, limit?, unread_only?, include_sent?, account?)` → per thread:
    `subject` (of the newest message, `Re:`/`Fwd:` stripped), `participants` (distinct
    addresses), `count`, `unread`, `first_date`, `last_date`, `complete`, and `messages`:
    `[{ mailbox, uid, date, from, message_id }]`, oldest first. Threads newest first by
    `last_date`.
  - `get_thread(mailbox, uid, account?)`: the thread of one message, every message in date
    order with its headers and **text body only** (HTML converted to text where there is no
    text part), each capped at 20,000 characters (`truncated: true`), the whole answer at
    100,000 characters. Attachments are listed as in `get_message`, never fetched. This is
    the call that replaces eight `get_message` calls.
- **B — `list_threads` only, returning ids.** Claude still makes one `get_message` per
  message: the cost #27 was filed against.
- **C — An opaque thread handle.** The connector would have to keep state between calls, or
  encode the whole id list into the handle. No gain over A's explicit references.

### 2.4 How an attachment is addressed (#28)

- **A — By its IMAP part id (recommended).** `get_message` reads `BODYSTRUCTURE` as well and
  reports each attachment's `part` (`"2"`, `"1.2"`) beside `filename`, `contentType` and
  `size`. `get_attachment(mailbox, uid, part)` downloads exactly that part (M5). Nothing
  else of the message is fetched.
- **B — By filename.** Two attachments can share a name, and many have none (M7).
- **C — By index into `get_message`'s list.** The list comes from mailparser, which has no
  part ids, so the index would have to be re-derived by parsing the whole message again on
  every download.

  With A, `get_message` reports `size` as the **decoded** size estimated from
  `BODYSTRUCTURE` (base64: × 3/4), since M3 shows the raw number is the encoded one.

### 2.5 What `get_attachment` returns (#28)

The issue says "base64". Base64 in a JSON text block is the one shape Claude cannot use:
a 1 MB PDF becomes 1.4 million characters of text, hundreds of thousands of tokens, and the
model cannot decode it.

- **A — Base64 in the JSON answer, as the issue says.** Rejected for the reason above.
- **B — An MCP content block chosen by type (recommended).**
  - `text/*`, `application/json`, `application/xml`, `text/calendar`: decoded to UTF-8
    (imapflow converts the charset) and returned as a `text` block, capped at 100,000
    characters with `truncated: true`.
  - `image/png`, `image/jpeg`, `image/gif`, `image/webp`: an `image` block.
  - Everything else, PDFs included: an embedded `resource` block with `blob` (base64),
    `mimeType`, and a `uri` of the form `imap://<account>/<mailbox>;UID=<uid>/;SECTION=<part>`
    (RFC 5092's shape; not fetchable, only a name).
  - Always a first `text` block with the metadata (`filename`, `contentType`, `size`,
    `part`), so a client that drops the other block still says what was attached.
- **C — B, plus text extraction for PDFs in the connector.** Needs a new dependency
  (`pdfjs-dist` or `unpdf`), runs CPU on untrusted input (it would belong in the worker pool),
  and duplicates what Claude does natively with a PDF. **Recommended out**, revisited only if
  A5 shows the claude.ai client does not hand an embedded PDF to the model.

### 2.6 How large an attachment may be (#28)

**Decided: B.** The ceiling is `MAIL_MCP_ATTACHMENT_MAX_MB` (a positive number, default 10),
read once at start in `src/config.ts`; a value that is not a positive number stops the start
and names the variable. Images are refused above 5 MB whatever the setting says (the Claude
API's per-image limit). Everything A says about checking before downloading, and about
`maxBytes` being the connector's own check, holds with the configured number in place of 10.

- **A — One ceiling for everything, checked before downloading (recommended).** The
  decoded size from `BODYSTRUCTURE` (§2.4) is compared with **10 MB** before any byte is
  fetched. Above it: a refusal naming the size and the limit, and suggesting forwarding
  (§2.7) instead. Images above **5 MB** are refused too (the Claude API's per-image limit).
  `download()` is still called with `maxBytes` of the ceiling plus one, and a download that
  reaches it is refused as "larger than its structure said": `maxBytes` truncates silently
  (M4), so the check is the connector's, not imapflow's.
- **B — A configurable ceiling** (`MAIL_MCP_ATTACHMENT_MAX_MB`). One more setting to
  document and test, for a number nobody has asked to change. Easy to add later.
- **C — No ceiling; stream whatever it is.** The failure #28 warns about: a 40 MB archive
  times out somewhere between the connector, the OAuth proxy and claude.ai, and says
  nothing useful.

### 2.7 Forwarding an attachment without it passing through Claude (#28)

"Forward this PDF to Anna" is the most likely request after "read this PDF", and the
request limit (5 MB, §0.1) means Claude cannot send back a file of any size it was given.

- **A — `send_message` and `create_draft` take `forward_attachments` (recommended):**
  `[{ mailbox, uid, part }]`, fetched server-side from the same account and attached with
  their filename and type. The same 10 MB ceiling applies, per attachment. `create_draft`
  gains the existing `attachments` too, which it lacks today.
- **B — Not in v0.8.** Forwarding works only for files small enough to pass through the
  request, which Claude cannot know in advance.

### 2.8 Who sends invitation mail for a meeting the account organizes (#29)

v0.7.4 made `notify_attendees` required whenever attendees are added or removed. Its
meaning today depends on the server: `true` on Nextcloud means "the server mails them", on
Radicale it means nothing happens.

- **A — The server only, as today.** iMIP is used only for answering (§2.10). On Radicale,
  `true` keeps meaning nothing.
- **B — The connector always.** Every attendee is written with `SCHEDULE-AGENT=CLIENT`
  and the connector mails them, on every server. One path, but on Nextcloud it throws away
  the server's scheduling, which also delivers to other Nextcloud users' calendars directly,
  and the mail would come from the connector's SMTP rather than from Nextcloud.
- **C — The server where it schedules, the connector where it does not (recommended).**
  `notify_attendees: true` means *they are told*, on every server:
  - **The server schedules** (its `DAV:` header carries `calendar-auto-schedule`, M11):
    attendees are written plainly, as today, and the connector sends nothing.
  - **It does not:** attendees are written with `SCHEDULE-AGENT=CLIENT` **and** an
    `X-MAIL-MCP-IMIP=TRUE` parameter, and the connector sends the iMIP mail itself.
  - `false` stays what it is: `SCHEDULE-AGENT=CLIENT` and no marker; nobody is told.

  **Never twice, by construction.** An attendee the connector mails always carries
  `SCHEDULE-AGENT=CLIENT`, so even a server that schedules without advertising it is asked
  not to mail them (RFC 6638), and an attendee written plainly is never mailed by the
  connector. The marker is what tells "the connector tells them" apart from "nobody tells
  them" on a later change. If another client strips the unknown parameter, the connector
  stops mailing that attendee: the failure leans to too little mail, never to double mail.
- **D — C, plus a per-account setting** to override the detection
  (`caldav.scheduling: "auto" | "server" | "connector"`). Not recommended for v0.8: an
  override is only needed if a server lies, and C's marker makes a lying server harmless.
  Added if acceptance finds one.

**The detection:** `OPTIONS` on the account's calendar home, once per client, cached like
`ownAddresses`. An `OPTIONS` that fails counts as "does not schedule" **and** the call is
refused when it would send iMIP, rather than guessing: *the connector could not tell whether
your calendar server sends invitations itself; nothing was sent or changed.*

**The sender:** the connector sends from the mailbox's `mail.defaultFrom`. iMIP is only sent
when that address is the event's `ORGANIZER` (by `addressKey`). Otherwise the call is
refused: an invitation whose `From` is not its organizer is shown as suspicious or "on
behalf of" by Gmail and Outlook, and replies go to the organizer address, which the
connector cannot read. On a non-scheduling server the organizer is `mail.defaultFrom` anyway
(R13 of v0.7.4: Radicale lists no `mailto:`), so this only bites an odd setup.

### 2.9 Which messages the connector sends, and when (#29)

Only where §2.8 makes the connector the scheduler, for attendees carrying the marker.

- **A — The whole object, every time (recommended).** RFC 5546 lets an organizer send the
  complete event as an update. So:
  - `create_event` with `notify_attendees: true` → `REQUEST` to every attendee.
  - `update_event` adding attendees → `REQUEST` to everyone marked, the new ones included
    (they need the whole event; the others see the guest list change).
  - Any other `update_event` or `delete_event` with `recurrence_id` on such an event →
    `REQUEST` with the whole updated object (the cancelled occurrence is an `EXDATE` in it)
    and `SEQUENCE` raised.
  - `remove_attendees` with `true` → `CANCEL` to each one removed.
  - `delete_event` of the whole event → `CANCEL` to every marked attendee.
  - `move_event` → nothing: the event did not change.
- **B — Per-occurrence messages** (`REQUEST` or `CANCEL` carrying only the one override or
  `RECURRENCE-ID`). Smaller mails, closer to what Nextcloud does, and a second set of
  builders and tests for every occurrence path v0.7.4 added.

  Either way: **the calendar write comes first, the mail second.** A mail that fails after a
  successful write is reported in the answer (`imip: { sent: [], failed: [{ to, reason }] }`)
  and the write stands; the connector does not undo a calendar change because SMTP was down.
  `may_notify` (v0.7.4) gains the marked attendees, and a new `notified_by: "server" |
  "connector"` says which of the two the call relied on.

  A copy of each sent iMIP mail goes to the Sent folder, as `send_message` does.

### 2.10 Answering an invitation (#29)

A new tool, `respond_to_invitation`, with `response: "accepted" | "declined" | "tentative"`
and an optional `comment`. Two sources:

- **From a received message** (`mailbox`, `uid`): the message's `text/calendar` part with
  `METHOD:REQUEST` (M6, M7).
- **From the calendar** (`calendar_url`, `uid`, `etag`, optional `recurrence_id`): an event
  someone else organizes, for instance one a scheduling server put there.

Who sends the `REPLY`:

- **A — Whoever delivered the invitation answers it (recommended).** The rule of §2.8,
  applied to the attendee side:
  - **The server delivered it:** the event is already in a calendar on a server that
    schedules, with a plain `ORGANIZER` (Nextcloud put it there, typically from another
    user of the same Nextcloud). The connector writes the account's own `PARTSTAT` there
    plainly, and the server sends the REPLY. It can deliver straight into the organizer's
    calendar, which mail cannot, and the connector sends nothing.
  - **Anything else** (an invitation that arrived as mail, or an event on a server that
    does not schedule): the connector sends `METHOD:REPLY` to the `ORGANIZER` over SMTP,
    and any calendar copy it writes or changes carries `ORGANIZER;SCHEDULE-AGENT=CLIENT`,
    so that no server answers as well. Whether Sabre would send a REPLY of its own when an
    attendee copy is *created* with a `PARTSTAT` is not documented; the parameter makes the
    question moot, and A10 checks that it does.
- **B — The connector always replies by mail**, and every calendar copy carries
  `ORGANIZER;SCHEDULE-AGENT=CLIENT`. One path, but an internal Nextcloud invitation answered
  this way never reaches the organizer's calendar: Nextcloud does not read iMIP mail.

**Whether the answered invitation goes into the calendar:** `add_to_calendar` (default true
when the account has a calendar). From a message, the event is created in the default (or
named) calendar if its UID is not there yet, and its `PARTSTAT` updated if it is. A
`SEQUENCE` older than the stored one is refused: *this invitation has been updated since;
read the newer one.*

The REPLY carries only the account's own `ATTENDEE` with its new `PARTSTAT`, the
`ORGANIZER`, `UID`, `SEQUENCE`, `DTSTAMP` and `RECURRENCE-ID` if one occurrence is answered,
per RFC 5546 §3.2.3. The account's own attendee is found by `addressKey` against its own
addresses; an invitation that does not list the account is refused (it was forwarded, not
sent to the account).

`get_message` gains an `invitation` field when the message carries a `text/calendar` part:
`{ method, uid, sequence, summary, start, end, organizer, attendees: [{ address, partstat
}], my_partstat }`, parsed with the existing ical modules. That is how Claude sees there is
something to answer, and it also makes a received `REPLY` or `CANCEL` readable.

### 2.11 An invitation from a mailbox that has no calendar (#29)

- **A — Out (recommended).** Without a stored event there is nothing to update or cancel
  later, and nothing to tell a second call what was sent. Answering invitations (§2.10)
  works for such a mailbox; sending them does not.
- **B — A `send_invitation` tool** that builds a one-off `REQUEST` from parameters. It would
  work once and leave every follow-up impossible.

### 2.12 #162: the wizard and the default mailbox

- **A — Only the first mailbox claims the default (recommended).** The wizard sends
  `default` only when the connector has no mailbox yet, which is what the connector's own
  *Add mailbox* form has always done (`src/settings-routes.ts:983`). The wizard already asks
  the connector which mailboxes exist for its step 3 (`fetchConfiguredMailboxes`,
  `oauth/src/setup-routes.ts:1129`); step 2 asks the same way. When the connector cannot be
  reached, the flag is sent, as today: on an empty instance that is right, and the store's
  rule from #139 (`find(a => a.default) ?? accounts[0]`) keeps a first mailbox the default
  even without it. The two sites name each other in a comment.
- **B — The wizard asks**, with a checkbox that is off on a second pass. A new form field
  and its round trip through the wizard's state, for a choice the full settings form already
  offers.
- **C — Leave it.** The issue's own reading of what the operator meant argues against it.

### 2.13 #182: how the provider tables are held together

- **A — One registry, with optional halves (recommended).** `PROVIDERS: Provider[]`, each
  with `id`, `label`, `source`, an optional `preset` and an optional `advice`.
  `MAIL_PROVIDERS` and `PROVIDER_ADVICE` become derived views with today's shapes, so no
  caller changes. A shared password clause is one string. The id list is pinned in order,
  the one-sided sets are enumerated literals in a test, and a unit test parses
  `docs/PROVIDERS.md`'s summary table and checks its first two columns against the registry
  in both directions (`test/unit/compose-data-volumes.test.ts` is the precedent).

### 2.14 #247: an `http://` CalDAV URL

Found by the security review of #220's fix. `parseCalDav` accepts `http://`, and the CalDAV
client then sends Basic auth in cleartext. Unlike #220 nobody forces it, the operator typed
it, but the exposure is the same.

- **A — #220's rule (decided).** `http://` is allowed only when the URL's host is local by
  `localMailAddress`'s rule in `src/mail-tls.ts` (an allow-listed address literal, or a
  local-form name that resolves only to local addresses). Otherwise:
  - **saving** a mailbox (settings form, wizard, JSON route) is refused with a message that
    says to use `https://`;
  - an **existing** `accounts.json` with such a URL still starts (an upgrade must not refuse
    to boot, #155), logs one `warn` per account at start, and every calendar tool on that
    account is refused with the same message until the URL is fixed. Mail tools are not
    affected.
- B — refuse at save only. C — refuse `http://` everywhere (breaks a local Radicale and the
  test stack).

## 5. Behaviour kept

- An update edits the stored object; it never rebuilds it. A marker added to an ATTENDEE
  keeps every other parameter.
- Every refusal is a `ToolRefusal` that ends by saying what was not done, and now also what
  was not sent ("Nothing was sent or changed.").
- Every tool that may make mail reach a real person says so and asks Claude to confirm with
  the user first. `respond_to_invitation` is one of them: a REPLY cannot be recalled either.
- The connector never sends iMIP to anyone a calendar server is free to schedule.

## 6. Risks

1. **Double invitations.** The worst failure here: two invitations, or a server cancellation
   plus a connector one. §2.8's rule (marker plus `SCHEDULE-AGENT=CLIENT` on every attendee
   the connector mails, and no connector mail to a plain attendee) makes it structural, and
   every path has a unit test asserting the pair. What no test here can show is that a given
   server honours `SCHEDULE-AGENT=CLIENT` on creation and on change: v0.7.4's A2 showed it
   on removal only. Acceptance A7 and A9 record it for Nextcloud.
2. **Mail that cannot be recalled.** iMIP mail is real mail to real people. Every new path
   is reached only through `notify_attendees: true` or `respond_to_invitation`, both
   described as needing the user's confirmation.
3. **Attachment size and context.** A 10 MB PDF as a resource block is still large; how
   claude.ai counts it against the context is not documented. A5 records what happens at
   1 MB and near the ceiling. If it fails badly, the ceiling comes down before release, not
   after.
4. **Prompt injection through attachments and threads.** Both new read tools return
   strangers' text in bulk. The descriptions say it is data; nothing more can be done in a
   connector, and nothing here acts on content without a further tool call.
5. **The thread window.** §2.1 A misses parents older than the window. `complete: false`
   says so instead of hiding it.
6. **A partial iMIP send.** The calendar write succeeded and the mail did not. Reported, not
   undone (§2.9). The model is told to say so to the user.
7. **Invitation formats.** Outlook and Gmail each have quirks (Outlook wants `method=` on the
   `Content-Type`, Gmail wants the `.ics` attachment too). nodemailer's `icalEvent` builds the
   shape both accept (M6); acceptance A7 checks Gmail. Outlook.com is a provider the
   connector cannot serve (docs/PROVIDERS.md), but an Outlook *recipient* is possible and is
   not tested here.

## 7. Testing

- **Pure logic, unit.**
  - Thread grouping: a thread out of order, a missing parent (`complete: false`), a cycle in
    `References`, a message with neither header, two threads with one subject (kept apart),
    a duplicate `Message-ID` across INBOX and Sent (counted once).
  - `BODYSTRUCTURE` walk: part ids, decoded size estimate, which parts are bodies.
  - iMIP builders: `REQUEST`, `CANCEL`, `REPLY` against hand-written fixtures. `REPLY`
    carries only the own attendee. `VALARM` is stripped from every outgoing message.
    `SEQUENCE` is raised on update.
  - The scheduling rule: for each combination of server-schedules × marker × `notify`, which
    attendees get `SCHEDULE-AGENT=CLIENT`, the marker, and connector mail. **No combination
    produces a plain attendee that the connector mails.**
- **Protocol, integration against GreenMail and Radicale** (the existing fixtures, 3143 and
  5232):
  - Threads: messages with real `References` delivered over SMTP, `list_threads` groups
    them, `include_sent` merges a `send_message` reply.

  - iMIP on Radicale, which does not schedule (M11): `create_event` with `true` puts a

## 9. Findings on `main` (not fixed here; in scope as noted)

Found while writing this spec, against `origin/main` at `9828068` (v0.7.4). Each is fixed
in v0.8 because a v0.8 tool builds on it, and each gets a test that fails on today's `main`.

- **F1. The Sent copy is a different message.** `src/tools-mail.ts:227` sends with
  `smtp.send()`, and `src/tools-mail.ts:248` builds the copy with `smtp.buildRawSource()`;
  each composition (`src/smtp-client.ts:70`, `:86`) invents its own `Message-ID` and `Date`
  (M8). A reply from the other side references the ID that went out, which the copy does
  not carry, so threads never connect to the copy (#27). The copy also loses `Bcc` (M8):
  the user cannot see from Sent whom they blind-copied.
- **F2. "Newest first" is oldest first in two cases.** `src/imap-client.ts:145` and `:182`
  reverse the UID list before fetching, but the server answers a `UID FETCH` in mailbox order
  (M9). `list_messages` with `unread_only`, and every `search_messages`, return their slice
  oldest first; `list_messages`' description says newest first.
- **F3. Previews are raw transfer encoding.** `src/imap-client.ts:305` fetches `BODY[1]`
  and `:343` turns the bytes into a string without decoding (M10). Quoted-printable and
  base64 bodies show as `Gr=C3=BC=C3=9Fe` or `R3LDtsOf…`, and for a `multipart` message part
  1 is the inner multipart, boundaries included.
- **F4. One field, two meanings.** `date` is the `Date` header in `list_messages` and
  `search_messages` (`src/imap-client.ts:351`) but the server's `INTERNALDATE` in
  `get_message` (`src/imap-client.ts:207`). For a message moved or appended later they
  differ, and a thread sorted by them would disagree with the list.
- **F5 (minor).** `create_draft` builds its message outside
  `reportingFailures()` (`src/tools-mail.ts:302`): a composition error reaches the client
  without the account named and without the one `warn` line #146 promises. One line to move;
  done in PR 3 of the plan only because the file is open.
