# v0.7.2 — The other half of the calendar — design

Status: drafted 2026-09-28, pending owner review.

Covers the whole v0.7.2 milestone: the two calendar tools that let Claude change and cancel
what it can already create, and the one regression the v0.7.1 acceptance run found.

Issues: #152 (`update_event`), #153 (`delete_event`), #197 (the wizard asks for a password
before it can say none will work).

Implementation plan: `docs/planning/plans/2026-09-28-v0.7.2-the-other-half-of-the-calendar.md`.

## 0. Problem

The calendar has four tools: `list_calendars`, `list_events`, `create_event` and
`find_free_slot`. **It can only add to a calendar.** Claude can put an appointment in a
calendar, and when it gets one wrong, fixing it means opening a calendar client by hand.
Mail has had `delete_message` since v0.1. The calendar stopped where v0.4 left it.

Two defects sit in the same code and have to be fixed before anything is built on it:

1. **`create_event` reports success on any HTTP answer.** `tsdav`'s `createCalendarObject`
   returns the raw `Response`; it does not throw on 4xx or 5xx. `CalDavClient.createEvent`
   never reads the response, so a `403 Forbidden` or a `507 Insufficient Storage` comes back
   to Claude as `{ success: true }`. `updateCalendarObject` and `deleteCalendarObject`
   behave the same way (verified in `node_modules/tsdav/dist/tsdav.cjs.js`, `updateObject`
   and `deleteObject`), so every write added here would inherit the bug.
2. **Nothing can test a CalDAV write.** `test/helpers/fake-caldav.ts` speaks no CalDAV on
   purpose: it answers `401` or `200 text/html`, which is all the probe needs. The existing
   four calendar tools have no end-to-end coverage at all. ETags, `If-Match` and `412` are
   exactly the behaviour a hand-written fake would get subtly wrong.

The third item comes from the v0.7.1 acceptance run (2026-09-28, point 4): the setup
wizard's address screen asks for a password, marked `required`, **before** the lookup that
tells an `@outlook.com` operator no password will work. The v0.7.1 spec, §5.3, said the
warning renders *"at address lookup — before any password is typed."* The warning is right
and appears once; the order is wrong. #120 moved the password onto the address screen to
avoid asking twice, and that decision won over §5.3 without anybody deciding it should.

## 1. Scope

**In:**
- `update_event` (#152) and `delete_event` (#153): ETag-guarded, UID-addressed, refusing
  single occurrences of a recurring series.
- `list_events` gains an `etag` field per event, so the two tools have something to guard
  with.
- Every CalDAV write checks the HTTP status, `create_event` included.
- A real CalDAV server in the integration fixture (Radicale).
- #197: the wizard's address screen stops asking for a password.

**Out:**
- **Notifying attendees.** Neither tool sends iMIP. An update or a cancellation reaches
  attendees only if their calendar server syncs it independently. That is #29 (v0.8), and
  both tool descriptions say so.
- **Editing or cancelling one occurrence of a series.** That is a `RECURRENCE-ID` override
  or an `EXDATE`, a different operation with its own failure modes. Both tools refuse it and
  say so (§4.3).
- **Changing the time of a whole recurring series.** See §4.3. Title, location and
  description of a series can be changed.
- **Attendees in `update_event`.** Adding or removing attendees without iMIP would produce
  invitations nobody receives. Existing attendees survive every update untouched.
- **Moving an event between calendars.** Not asked for, and a CalDAV `MOVE` between
  collections is a separate protocol question.

## 2. Decisions for the owner

These were decided while writing the spec and are the ones worth a second look before
implementation starts:

1. **The ETag comes from the caller, not from a fresh read.** `update_event` and
   `delete_event` take the `etag` that `list_events` returned. The tool sends *that* value as
   `If-Match`. Reading the object again and using its current ETag would only protect the
   few milliseconds between the tool's own GET and PUT, and would still silently overwrite a
   change made from a phone between Claude's `list_events` and its `update_event`. That
   second case is what #152 names.
2. **A recurring series needs `apply_to_series: true`.** An event reached through
   `list_events` is an expanded instance. A model that wants to move "the meeting on
   Thursday" and passes that instance's UID would otherwise change every occurrence. Without
   the flag, both tools refuse on a recurring event and say it is a series.
3. **A series' time cannot be changed in this version.** An instance's start is not the
   series' `DTSTART`. Deciding what "move this series to 15:00" means (the first
   occurrence? every occurrence, keeping the date?) is a design problem of its own, and a
   wrong guess moves every meeting in a series. `update_event` refuses `start`, `end` or
   `all_day` on a series and says which fields it will accept. This goes further than #152,
   which says "handles the series". Relaxing it later is a feature; a wrong guess now is data
   loss.
4. **New times are written in UTC.** `create_event` already writes `DTSTART`/`DTEND` as UTC.
   An update that changes the time does the same, and drops the `TZID` parameter on those two
   properties only. The event keeps its instant; a client shows it in the viewer's zone.
   Converting into the original `VTIMEZONE` would need that zone registered with `ical.js`,
   and zones are exactly where hand-rolled conversion goes wrong. An update that does not
   touch the time leaves `DTSTART`/`DTEND` and their `TZID` exactly as they were.
5. **#197: remove the password from the address screen**, rather than making it optional.
   An optional box still invites typing a password for something that cannot work. Every
   screen after the lookup already asks for a missing password (see §5).

## 3. The tools

### 3.1 `list_events` — one new field

Each event gains `etag: string | null`: the object's ETag exactly as the server sent it,
quotes included, or `null` when the server sent none. Instances expanded from one series
share their object's ETag. The field is additive; no existing field changes.

### 3.2 `update_event`

| Parameter | Type | Notes |
|---|---|---|
| `calendar_url` | url | as returned by `list_calendars` |
| `uid` | string, min 1 | as returned by `list_events` |
| `etag` | string, optional | as returned by `list_events`; see §4.1 |
| `summary` | string, min 1, optional | |
| `description` | string, optional | `""` removes it |
| `location` | string, optional | `""` removes it |
| `start` | ISO datetime, optional | alone, it moves the event and keeps its duration |
| `end` | ISO datetime, optional | |
| `all_day` | boolean, optional | changing it requires both `start` and `end` |
| `recurrence_id` | string, optional | exists only to be refused (§4.3) |
| `apply_to_series` | boolean, optional | required for a recurring event |
| `account` | as everywhere | |

At least one of `summary`, `description`, `location`, `start`, `end`, `all_day` must be
given. Otherwise the call is refused with nothing changed.

Answer: `{ success: true, uid, url, etag }`, where `etag` is the new ETag from the `PUT`
response's `ETag` header, or `null` when the server sent none.

Description, in substance: *"Change an existing event. WRITE OPERATION. Pass the `etag` from
`list_events`; if the event changed since, nothing is written and you are told to re-read
it. Attendees are NOT notified of the change: this connector does not send iMIP yet.
Fields you do not pass are left exactly as they are, including attendees, alarms and
recurrence rules."*

### 3.3 `delete_event`

Parameters: `calendar_url`, `uid`, `etag` (optional, §4.1), `recurrence_id` (refused),
`apply_to_series`, `account`. Answer: `{ success: true, uid, url }`.

The description has to say plainly: *"PERMANENT. CalDAV has no trash: a deleted event cannot
be recovered. Attendees are NOT sent a cancellation. For a recurring event this deletes
every occurrence."* A model that believes it can undo a delete will use it more casually
than it should (#153).

## 4. Behaviour

### 4.1 Concurrency

- The caller's `etag` is sent as `If-Match` on the `PUT` or `DELETE`. A `412` becomes the
  conflict refusal: *nothing was changed; call `list_events` again for the current state and
  etag, then retry.*
- **`etag` omitted, server has one for the object:** refused, and the refusal asks for the
  etag. The parameter is optional only so the next rule is possible.
- **`etag` omitted, server has none:** the write goes ahead without `If-Match`. Some servers
  send no ETags. A tool that refused them outright would be unusable there, and there is
  nothing to compare against anyway.
- An `If-Match` `PUT` against an object that has vanished answers `412`, not `201`
  (verified against Radicale 3.8.1), so an update can never create an event.

### 4.2 Finding the event

The event is found by UID inside the named calendar: a `calendar-query` `REPORT` with a
`prop-filter` on `UID` (`tsdav`'s `fetchCalendarObjects` with custom `filters`). RFC 4791's
`text-match` is a **substring** match, so `ev1` would also match `ev10`. Every result is
re-checked for an exact UID before it is used.

No match: *No event with UID … in calendar …. Nothing was changed, and no event was
created.* (`delete_event`: *Nothing was deleted.*) A `404` on the write itself (deleted in
between) gets the same answer.

### 4.3 Recurrence

An object is **recurring** if its main `VEVENT` (the one without `RECURRENCE-ID`) carries
`RRULE` or `RDATE`, or if any `VEVENT` in it carries a `RECURRENCE-ID`.

| Call | Answer |
|---|---|
| any call with `recurrence_id` | refused: single occurrences are not supported yet. `update_event` says an override is needed; `delete_event` says it would be an `EXDATE`. Nothing changed. |
| recurring, no `apply_to_series` | refused: this is a series and the change would apply to every occurrence; pass `apply_to_series: true` if that is intended. |
| recurring, `apply_to_series`, touches `start`/`end`/`all_day` | refused: the time of a whole series cannot be changed yet; `summary`, `description` and `location` can. |
| recurring, `apply_to_series`, text fields only | applied to the main `VEVENT` only. Overrides keep their own values. |
| `delete_event` recurring, `apply_to_series` | the whole object is deleted. |

### 4.4 What an update preserves

The update edits the stored object; it does not rebuild it. It is parsed with `ical.js`, the
main `VEVENT` for the UID is modified in place and the result is serialised. Everything else
survives byte-for-byte in meaning: `VTIMEZONE`, `VALARM`, `ATTENDEE` with every parameter
(`PARTSTAT`, `CN`, `ROLE`), `ORGANIZER`, `CATEGORIES`, `X-` properties and the override
`VEVENT`s. This is the property #152 names as the failure mode to design against.

Every successful update also:
- raises `SEQUENCE` by one (absent counts as `0`), as RFC 5545 §3.8.7.4 asks when the
  organizer changes an event;
- sets `DTSTAMP` and `LAST-MODIFIED` to now, in UTC.

A time change removes `DURATION` if present and writes `DTEND`. `start` alone keeps the
duration: an hour-long meeting moved to 15:00 still ends at 16:00. For all-day events the
duration is counted in days. The merged `end` must be after the merged `start`; otherwise
the call is refused and nothing is written.

### 4.5 Errors: an answer versus a failure

Every refusal above is an answer, not a mailbox failure. It must not produce the `warn` line
`reportingFailures()` writes (#146): a model retrying after a conflict is working as designed.
A logged conflict would teach operators to ignore the one log line that matters. So:

- **`ToolRefusal`**, a new `Error` subclass in `src/tool-errors.ts`. `reportingFailures()`
  rethrows it unchanged, with no log line, and with its message intact rather than prefixed.
- Any other non-2xx status from a CalDAV write becomes an ordinary `Error` naming the method
  and the status (`CalDAV server answered 403 Forbidden to PUT`). It goes through
  `reportingFailures()` like any server failure and is logged once. `create_event` gains the
  same check.

## 5. #197 — the address screen

`renderMailboxAddressStep` drops the password box and its hint. The screen asks for the
address only. Every way out of the lookup already handles an empty password:

- **Found settings.** `suggestionPassword("")` renders its own `required` password box with
  the text that it is stored only once the servers answer (`oauth/src/setup-pages.ts`,
  `suggestionPassword`). The unsupported-provider warning is on this same screen, above the
  box. That is the order §5.3 asked for.
- **Nothing found → provider list → form**, and **Enter all the settings myself → form**:
  the form's own IMAP and SMTP password boxes are `required`.

#120 stays fixed trivially: the password is asked exactly once, on the first screen that
needs it, and from there on the existing carrying rules apply (`withCarriedPasswords`,
the hidden field on the confirmation screen, `Edit these`).

The docstring on `renderMailboxAddressStep` currently argues the opposite ("a screen that
asks for an address, goes away for up to ten seconds and then asks for a password reads as
two steps rather than one"). It is rewritten to cite §5.3 and #197, so the reasoning is not
re-litigated by the next reader.

**Tests to change, not delete:**
- the address-screen unit test *"asks for two things, not eighteen"* becomes *one thing*, and
  asserts the password box is absent;
- *"never writes a password back into the page"* on the address screen becomes moot, and
  moves to the confirmation screen's empty case;
- the integration test *"the password typed on the address screen is not asked for a second
  time"* (#120 end to end) becomes: the password typed on the confirmation screen reaches the
  save, and is not asked for again on `Edit these`;
- the Outlook test (*"an outlook.com address is called out at the lookup"*) additionally
  asserts that the request that produced the warning carried no password field.

Only one browser-level fact changes: Enter in the address box still submits `lookup` (the
existing #140 test keeps guarding that).

## 6. Testing

- **Pure logic, unit:** a new `src/ical-edit.ts` holds the parsing and merging, with no
  network access. It is where preservation, `SEQUENCE`, duration and recurrence detection are
  proven, against hand-written ICS fixtures that carry every property §4.4 lists.
- **Protocol, integration:** Radicale joins `docker-compose.test.yml` on port `5232`, pinned
  by digest (`tomsquest/docker-radicale@sha256:419e0c005b63bd475d50f73c5e7ff2b1f04924edb94af525fa86faed213c632a`,
  Radicale 3.8.1). Its default config has `auth = none`, so any Basic credentials are
  accepted and the username becomes the collection owner. Each test run uses a fresh random
  user, so no state leaks between runs. CI needs no change: `_test.yml` already runs
  `docker compose -f docker-compose.test.yml up -d`, which starts every service in the file.
- Verified by hand against that image on 2026-09-28: a stale `If-Match` answers `412` on both
  `PUT` and `DELETE`; `If-Match` on a missing object answers `412`; a plain `DELETE` of a
  missing object answers `404`; a `calendar-query` with a UID `prop-filter` returns the
  object's href and ETag.
- **Tool surface:** `mcp-protocol.test.ts`'s expected list grows from 14 to 16 names.

The integration suite is serialised (`--test-concurrency=1`) and binds fixed ports. Radicale
adds `5232` to the ports two worktrees cannot share (see the parallel-waves note in the
maintainer's memory: stagger integration runs across agents).

## 8. Acceptance

Per issue, as written in #152, #153 and #197. The milestone additionally closes only when
it is run **on the Hetzner instance** (a playground until v1.0.0, so no separate instance):

1. `docker compose down -v` in `~/mail-mcp`, fresh wizard: an `@outlook.com` address reaches
   the warning with no password typed anywhere (#197).
2. With a real CalDAV account configured (Nextcloud, Fastmail, iCloud or mailbox.org),
   through Claude: create an event, move it by an hour, rename it, delete it. Each step is
   checked in that provider's own calendar UI.
3. An event carrying a reminder and an attendee, created in the provider's UI, is renamed
   through `update_event`. The reminder and the attendee are still there afterwards.
4. The same event is edited in the provider's UI between `list_events` and `update_event`:
   Claude is told it changed, and the provider's version survives.
5. A recurring event is refused without `apply_to_series`, and its time is refused with it.
