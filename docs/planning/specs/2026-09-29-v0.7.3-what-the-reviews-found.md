# v0.7.3 — What the reviews found — design

Status: written 2026-09-29. §2 holds no decision for the owner: each choice below is one the
issue already made or one it left to the implementer, and the reasoning is written down so it
can be overruled in review.

Covers the whole v0.7.3 milestone: three operator-visible gaps the v0.7.1 reviews and its live
verification turned up, and deliberately did not hold that release for.

Issues: #172 (one predicate written twice, one field with no reader), #173 (a bypassed probe
leaves no trace, and the CalDAV-saved 200 keeps the POST URL), #194 (the address lookup
suggests an SMTP port this host cannot reach).

Implementation plan: `docs/planning/plans/2026-09-29-v0.7.3-what-the-reviews-found.md`.

## 0. Problem

v0.7.1 fixed the case that opened it: a rejected password is refused at save time, names the
mailbox and leaves one log line. Three things one layer down are still wrong.

1. **A CalDAV block that does not work is shown on one screen and hidden on the other.** The
   connector's settings form saves the mailbox and shows `caldavFailureNotice`. It shows it on
   a `200` rendered straight out of the `POST`, so a reload re-submits the form: on create a
   second 25-second probe and then a `409`, on edit a `409` and the edit URL left in the address
   bar (#173 item 4). The setup wizard saves the same mailbox through the JSON route, receives
   the same report in the `201` (`MailboxCreatedAnswer.probe`), throws it away and redirects to
   step 3 in silence (#172 item 2). One outcome, two UIs, two different amounts of truth.
2. **A save that bypassed the probe leaves no trace in the connector's log** (#173 item 3). The
   wizard path logs `probed: !saveAnyway`, but the settings-UI path logs nothing on a successful
   write. That is the path used for every mailbox after the first. An operator whose mailbox
   fails every tool call cannot tell from the log whether it ever authenticated.
3. **The address lookup can suggest a port the host cannot reach while the connector's own
   table holds one it can** (#194). On Hetzner, outbound 465 and 25 are blocked. The Mozilla
   ISPDB answers `gmail.com` with `smtp.gmail.com:465` only, while `src/providers.ts` holds
   Google's documented `587`/STARTTLS. The v0.7.1 live run connected over IMAP and failed over
   SMTP for exactly that reason.

Plus the debt #172 lists in the wire contract: `probeRefusesSave(r)` is `saveRefusedNotice(r)
!== null` written twice, and three call sites each discard the other's `null` differently. The
connector's `?? ""` paints an empty grey notice box, and the wizard has a fallback sentence of
its own.

## 2. Choices made here

None needs the owner. Each is written out so review can overrule it.

### 2.1 The CalDAV notice survives the redirect as a one-shot flash (#173.4)

The issue offers two shapes: a flash on the server, or `?saved=caldav-failed` that the list
route turns back into the sentence. The sentence carries `caldav.message`, the server's own
words about what failed ("401", "not a calendar", a host name). A query flag cannot carry those
words. Putting them *in* the query would let any link paint arbitrary text into an operator's
settings page, and that is content injection on the one page that holds mail passwords.

**Chosen:** the connector keeps a small in-memory map `token → notice`, with a random 128-bit
token, a TTL of 10 minutes and at most 32 entries (the oldest is evicted). It redirects `303` to
`/settings/mailboxes?notice=<token>`. The list route renders the notice when the token is known,
and a reload after the TTL shows the plain list. An unknown token is ignored, not answered with
an error: a bookmarked URL is not a fault. The token is not consumed on first read, so a reload
within the TTL shows the same page. That is what "reload shows the list, not a resubmission"
means.

`sendSavedPage` then has no `200` branch left. Both write routes end in the same `303`, and
the doc comment's double-submit claim becomes true without an exception.

### 2.2 The wizard carries the notice onto step 3 the same way (#172.2)

The issue prefers wiring the wizard up over dropping the field. **Chosen: wire it.** The wizard
reads the `201` with `parseCreatedAnswer`. When `probe` carries a failed CalDAV, the wizard
holds `caldavFailureNotice(probe)` as a one-shot pending notice in its own closure. The `GET` of
step 3 shows it as an `info` notice. It is not an `error`: the mailbox *was* saved, and step 3's
job is to finish. It is shown once and cleared on the next render, which suits a wizard that
runs once per instance. It is not a map, because the wizard has one operator and one claim token.

An unreadable `201` body still counts as stored. That is #82's rule and it stays: the status is
the fact. An unreadable body just carries no notice.

### 2.3 One predicate, one sentence (#172.1)

`saveRefusal(report, credentialNote?, addressWarned?): string | null` replaces both
`probeRefusesSave` and `saveRefusedNotice`. It is the gate (`!== null`) and the text. Three call
sites lose their `?? …`:

- connector create/edit: `refusalNotice` returns `string | null`, and the form renders no notice
  box for `null` (the empty grey box goes).
- wizard: the fallback sentence `"Nothing was saved. Fix what failed above and try again."` is
  deleted. The report the wizard holds is a refusal by construction, so `saveRefusal` never
  returns `null` there. The type still has to say so, with a single non-null assertion
  commented as such, not a second sentence.

`credentialRejectionRefusesSave`, `probeFailed` and `anyCredentialRejection` stay. They answer
different questions, and their docs say why.

### 2.4 Reachability at lookup is a connect, not a login (#194)

As the issue decided: a TCP connect, then a TLS handshake for implicit TLS. The handshake
verifies the certificate against the host name, exactly as the real connection later will. A
candidate that would fail there must not win here. For STARTTLS it is
the connect plus the server's greeting (`220` for SMTP, `* OK` for IMAP), without negotiating
STARTTLS itself. A port that is filtered, as on Hetzner, fails at the connect, and that is the
case this exists for. No credential is sent at lookup. A provider that rate-limits failed logins
is never charged one per candidate.

### 2.5 The budget moves by one probe slice rather than squeezing probes into the remainder (#194)

The probes run in parallel: every candidate for IMAP and SMTP at once, each with its own
`LOOKUP_PROBE_TIMEOUT_MS` of 3 s. They run after discovery, not inside its budget.
`CONNECTOR_AUTOCONFIG_BUDGET_MS` becomes 10 s of discovery plus 3 s of probing = **13 s**, and
the wizard's `LOOKUP_TIMEOUT_MS` follows by derivation, as #134 built it to. The alternative,
probing in whatever budget discovery left, makes the suggestion depend on how slow the ISPDB was
that minute. At most **4 candidates per service**. The worst case is bounded at 13 s plus the
unwind, and a test states it.

### 2.6 Ordering and the no-answer case (#194)

- Candidates are ranked by today's `best()` score (password auth, then implicit TLS over
  STARTTLS). Reachability picks the **first reachable in that order**, so a host where both 465
  and 587 answer still gets 465.
- When none answers, the top-ranked candidate is suggested exactly as today. The probe at save
  then reports the failure per service, as it does now. The lookup never turns "SMTP did not
  answer" into "tried several things".
- A candidate whose host resolves to a non-public address (`isPublicIp`) is **not** connected to
  at lookup. It stays in the ranking and counts as "not known to be unreachable". Two reasons:
  the lookup is fed by documents from hosts the operator typed, and this keeps the lookup from
  becoming a port scanner of the connector's own network. A self-hoster's LAN mail server is
  still suggested, just not pre-checked.

## 3. #194 — where candidates come from

Today each source yields one server per service, and the first source that yields both wins.
After this change the winning source yields a **ranked list per service**, and two more sources
are merged in:

| Source | Today | After |
|---|---|---|
| autoconfig / well-known / ISPDB document | `best()` of the blocks | every usable block, ranked |
| RFC 6186 SRV | `_submissions`, else `_submission` | both, when both exist |
| `src/providers.ts` preset for the address's domain | not consulted | appended, deduplicated by host+port |

The domain → preset mapping goes through `PROVIDER_ADVICE`'s `domains` and the matching
`MAIL_PROVIDERS` entry with the same `id`. Only providers with both exist, today Gmail. A preset
is appended only when discovery found *something*. The lookup's `null` still means "show the
provider list", and the table is what that list is made of.

The `source` of the suggestion stays the tier that answered. Which candidate won is logged at
`info` as `{ service, candidates, chosen, reachable }`, with host:port pairs and no address or
local part.

## 4. #173.3 — the log line

Both connector write routes log on success:

```
info  settings: a mailbox was saved  { action: "create"|"edit", id, probed: boolean }
```

Booleans and the account id only, as on the refusal line beside it. `probed` is `false`
precisely when `readSaveAnyway` returned true. The line is written in `gateOnProbe`'s caller
after the store call returned, never before, so it cannot claim a save that then hit a `409`.

## 6. Testing

TDD throughout: each behaviour gets a test that is seen failing before the change.

- Unit, `test/unit/settings-api.test.ts`: `saveRefusal` covers every case the two old functions
  covered (the existing cases are renamed, not deleted). Plus `null` for a CalDAV-only failure.
- Unit, `test/unit/autoconfig.test.ts`, with injected deps plus an injected `reachable(host,
  port, socketType)`:
  - ISPDB 465 unreachable plus a table 587 reachable gives 587/STARTTLS.
  - Both reachable gives 465.
  - None reachable gives 465, exactly today's answer.
  - A domain in no table with one candidate is unchanged.
  - Both SRV submission records are candidates.
  - A private-address candidate is never connected to.
  - At most 4 candidates per service reach the probe.
  - The whole lookup resolves within 13 s against a `reachable` that never settles.
- Unit, `test/unit/lookup-reachability.test.ts`: the real `reachable` against a local
  `net.Server` (greeting `220`), a `tls.Server` (self-signed: reachable only when the test hands
  its cert in as the trusted CA, unreachable otherwise) and a closed port.
- Integration, `test/integration/settings-mailboxes.test.ts` (fake servers, not GreenMail):
  - A CalDAV-failed create/edit is a `303` to `?notice=`, and the `GET` shows the sentence.
  - The same `GET` after the TTL (clock injected) shows none.
  - An unknown token shows none.
  - Every successful write logs `probed`.
- oauth integration, `oauth/test/integration/setup-wizard.test.ts`: a `201` carrying a failed
  CalDAV makes step 3 show the notice once. A `201` with no probe or an unreadable body shows
  none, and still advances.
- The derived-budget test (#134) still passes, with the new number.
