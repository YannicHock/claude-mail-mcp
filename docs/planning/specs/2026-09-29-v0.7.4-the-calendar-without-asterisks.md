# v0.7.4 — The calendar without asterisks — design

Status: approved 2026-09-29. All decisions in §2 confirmed by the owner as written.

Covers the whole v0.7.4 milestone. After it, none of the limitations the v0.7.2
acceptance run listed remain. The owner decided on 2026-09-29 to close the list as one
patch rather than theme by theme.

Issues: #203 (the connector's Add-mailbox page asks for a password first), #204
(ORGANIZER), #205 (attendees in `update_event`), #206 (one occurrence), #207 (a series'
time), #208 (keep the time zone), #209 (floating and unresolved zones), #210 (ETag edge
cases), #211 (lookup robustness), #212 (move between calendars), #213 (`find_free_slot`),
#214 (test gaps and cleanups).

Implementation plan: `docs/planning/plans/2026-09-29-v0.7.4-the-calendar-without-asterisks.md`.

## 0. Problem

v0.7.2 gave the calendar its other half, `update_event` and `delete_event`, and was honest
about what they refuse: a single occurrence, a series' time, attendees, zones the connector
cannot place. The acceptance run on Nextcloud added one fact that changes how much of this
is data work: **the calendar server sends mail on its own.** Nextcloud mails the attendees
of an event you organize when it changes or is deleted. Anything that touches ORGANIZER or
ATTENDEE decides whether real people get mail.

Writing this spec against a real Radicale 3.8.1 turned up **three more defects on today's
`main`**. Each one takes down `list_events` for a whole calendar, not just for one event
(§0.1). They are not in any of the twelve issues, but they sit on the read path that #206,
#207 and #213 build on, so this spec fixes them instead of filing a thirteenth issue.

### 0.1 What Radicale showed (verified 2026-09-29)

Everything below was run against the pinned image
`tomsquest/docker-radicale@sha256:419e0c00…` (Radicale 3.8.1). It was started as a
separate container on port 5233, so that a parallel run of the integration suite on 5232
was not disturbed. The probes were throwaway scripts: raw HTTP, and `CalDavClient` itself
through `tsx`. The results:

| # | Probe | Result |
|---|---|---|
| R1 | `list_events` over a calendar holding an **all-day weekly series** | **Throws** `invalid date-time value: "2026-10-01T::"`. Radicale's server-side expansion writes `RECURRENCE-ID:20261001` without `VALUE=DATE`, and ical.js cannot decorate that value. The whole calendar fails. |
| R2 | `list_events` over a calendar holding a **floating weekly series** | **Throws** `Collection query failed: 500`. Radicale's expansion crashes (`can't compare offset-naive and offset-aware datetimes`, from the server log). |
| R3 | `list_events` over a calendar holding an **override-only object** (one VEVENT with a RECURRENCE-ID and no master; the shape of an invitation to a single instance) | **Throws** `400 Bad Request`. Radicale refuses the whole expand REPORT ("does not have a vevent without a recurrence_id"). |
| R4 | The same three calendars through a `calendar-query` with a `time-range` and **no** `expand` | 207, every object returned, including the floating series in a window that holds only its second occurrence. |
| R5 | Server expansion of a TZID series with EXDATE and one override | Correct: RECURRENCE-ID and DTSTART come back in UTC, the EXDATE is left out, the override is used, and the DST change on 2026-10-25 is applied. |
| R6 | A `TZID=Europe/Berlin` series with **no VTIMEZONE** in the object | Radicale stores it and expands it correctly (it resolves IANA names itself). ical.js, parsing the same object, reads the TZID as **floating**. `TimezoneService.register` fixes that, but only process-wide. |
| R7 | An object whose object href has **no `.ics`** | Stored. `list_events` returns 0 events, and `update_event` by UID answers "No event with UID…" (#211.1 confirmed). tsdav's default `urlFilter` drops the href. |
| R8 | `update_event` on an **override-only object** | Refused as "a recurring series… pass apply_to_series" (#211.3 confirmed, the misleading branch). |
| R9 | `If-Match` with the quotes stripped, and with `W/` in front of the ETag | 412 for both (#210.2 and #210.3 confirmed). |
| R10 | `If-Match: *` on PUT | **412 on an existing object as well as on a missing one.** Radicale compares `*` literally on PUT (`radicale/app/put.py`). DELETE handles `*`, and a PUT with no `If-Match` onto a missing name answers 201, so it creates. |
| R11 | `MOVE` between two calendars of one user | 201, the ETag is unchanged, VALARM and `ATTENDEE;PARTSTAT=…` survive. **`If-Match` on MOVE is ignored:** a MOVE with a stale ETag moved the object (`move.py` has no precondition code). `Overwrite: F` onto an existing name gives 412. A UID the target already holds gives `409 <C:no-uid-conflict/>`. |
| R12 | `free-busy-query` REPORT | 200, but **not the RFC 4791 §7.10 shape**: one VFREEBUSY *per event*, each with DTSTART/DTEND/FBTYPE, and no `FREEBUSY` periods. `TRANSP:TRANSPARENT` is left out, `STATUS:CANCELLED` is reported as `FBTYPE:FREE`, and `STATUS:TENTATIVE` as `BUSY-TENTATIVE`. |
| R13 | The principal's `calendar-user-address-set` | Only the principal href (`/user/`), with **no `mailto:`**. No schedule inbox or outbox. `calendar-timezone` on a collection: 404. |
| R14 | `find_free_slot` on an empty calendar, Monday to Wednesday, working hours 9–17 | **One slot, Monday only.** Tuesday and Wednesday are lost: `clampToWork` clips a free gap to the first day it starts on. That is a fourth defect, not in #213's list. |
| R15 | `find_free_slot` with a transparent 10–12 and a cancelled 13–14 | Both block time (#213 confirmed). |
| R16 | An object ical.js cannot parse (`X-FOO;BAR:val`, a parameter with no value) | Radicale accepts it with 201, **but it normalises what it stores through vobject**. The stored object parses fine, so the "one bad object" of #211.2 cannot be planted in Radicale by content. It is tested behind a proxy instead (§6). |

The ical.js and time-zone checks:

- **Orphans are real.** A weekly series has one EXDATE; move only its DTSTART by 6 h, and
  the cancelled occurrence comes back (2 → 3 occurrences).
- **UNTIL can lose an occurrence.** A series with `UNTIL` equal to its last start loses
  that last occurrence when DTSTART moves later (4 → 3).
- **The candidate time-zone package is wrong.** `timezones-ical-library` 2.3.2 publishes
  VTIMEZONE blocks. Checked against `Intl` (ICU 78.3, in Node 24) every day for 2026–2030,
  it is exact for Berlin, New York, Sydney, Kolkata and São Paulo. It is **wrong for
  Jerusalem on 14 days and for Casablanca on 1,627 of 1,826 days**: rule-based blocks
  cannot express irregular zones.
- **`Intl` gives the exact offset at every instant, in every IANA zone.** Converting
  wall-clock time *to* an instant still needs RFC 5545 §3.3.5's rule at the two edges. In
  the DST gap, the offset from before the gap is used. In the overlap, the first
  occurrence is used. A naive two-step conversion picked the *second* occurrence in the
  overlap (Berlin 02:30 on 2026-10-25 gave 01:30Z, not 00:30Z), so the rule is pinned by a
  test (plan, Task 2).

## 1. Scope

**In:** all twelve issues, plus the four defects §0.1 found (R1, R2, R3, R14):
- `list_events` stops failing a whole calendar over one object (R1–R3, #211).
- ORGANIZER and attendees (#204, #205).
- One occurrence (#206) and a series' time (#207).
- Zones kept, floating times kept, IANA zones resolved (#208, #209).
- ETag edge cases (#210) and lookup robustness (#211).
- `move_event` (#212).
- `find_free_slot` (#213, plus R14).
- Test gaps and cleanups (#214).
- #203, the Add-mailbox page.

**Out, explicitly:**
- **iMIP** (#29, v0.8). The connector itself still sends no invitation, update or reply
  mail. What changes is that it now decides, per call, whether the *server* may (§2.1).
- **Tasks / VTODO** (#215, v0.9).
- **Answering an invitation** (setting your own `PARTSTAT`). On Nextcloud that makes the
  server send a REPLY; it belongs with #29.
- **"This and all following occurrences"** (a series split). See §2.4, option C. Not one of
  the twelve.
- **Changing the day of a series** (Thursday → Friday). That is an RRULE rewrite, not a time
  change. See §2.4. Not one of the twelve.
- **Creating a recurring event.** `create_event` has no RRULE parameter today. Not one of the
  twelve. It would be a new issue if wanted.
- **Moving an event across accounts.** #212 excludes it.
- **Windows zone names** (`W. Europe Standard Time`) in a TZID **with no VTIMEZONE**. The
  refusal stays, as #209 asks. With a VTIMEZONE in the object they already work.

## 2. Decisions for the owner

Each decision lists its options and a recommendation. **Nothing in the rest of this spec is
final until these are confirmed.** Sections 3–5 are written against the recommendations.

### 2.1 Who may make the calendar server mail people (#204, #205)

Nextcloud (Sabre's scheduling plugin, RFC 6638) mails attendees when an event whose
ORGANIZER is the account's own address is created, changed or deleted. Radicale mails no one
(R13: it has no schedule outbox). RFC 6638 gives the client one lever: the parameter
`SCHEDULE-AGENT=CLIENT` on an ATTENDEE says *the client handles this attendee; the server
sends it nothing*.

- **A — Let the server schedule, always.** Attendees are written plainly. On Nextcloud,
  `create_event` with attendees sends invitations, and removing one sends a cancellation.
  The tool texts say so, and "confirm with the user first".
- **B — Never let the server schedule.** Every attendee the connector writes carries
  `SCHEDULE-AGENT=CLIENT`. Attendees are recorded and never told, until #29 sends iMIP
  itself. It is quiet, but a user who asks Claude to "invite Anna" gets an event Anna never
  hears of.
- **C — The caller decides, every time (recommended).** Every call that adds or removes
  attendees has to state its intent: `create_event` with `attendees`, and `update_event`
  with `add_attendees` or `remove_attendees`. It does that with a **required**
  `notify_attendees: boolean`:
  - **`true`** writes the attendees plainly. The description says the server may mail them
    an invitation or a cancellation, and that this cannot be recalled.
  - **`false`** writes `SCHEDULE-AGENT=CLIENT` on the attendees being added. The event
    lists them and nobody is told.

  A required flag makes "confirm with the user first" structural. The model cannot add a
  person without saying which of the two it means.

  Removal with `false` is honoured only if the Hetzner run (A2) shows that Nextcloud sends
  no cancellation for an attendee who carried `SCHEDULE-AGENT=CLIENT`. Otherwise
  `remove_attendees` with `false` is refused, with the reason.

**ORGANIZER, whatever is chosen above:**
- **Recommended:** write `ORGANIZER` whenever an event has attendees. RFC 5545 requires it,
  and without it Nextcloud does not treat the event as a meeting at all (#204).
- **Which address.** Take the first `mailto:` in the principal's
  `calendar-user-address-set`. Fall back to the account's `mail.defaultFrom`, because
  Radicale lists none (R13). The principal's own address is the one Sabre compares against
  to decide "you organize this". A Gmail mailbox with a Nextcloud calendar has two
  different addresses, and the mailbox one would make Nextcloud treat the event as an
  invitation *received*.
- **Someone else's meeting.** Adding or removing attendees on an event whose ORGANIZER is
  somebody else is **refused**: only the organizer changes the guest list. Text changes to
  such an event stay allowed, as today. They are local, and the v0.7.2 texts already warn.
- **An older event with attendees and no ORGANIZER** (written by `create_event` before
  v0.7.4) gets one the first time its attendees change.

**What the tool texts say** (all four writing tools, and `move_event`): *"This connector
sends no mail itself. Your calendar server may: Nextcloud emails attendees of an event you
organize when it is created, changed, moved or deleted. That mail cannot be recalled.
Confirm with the user before changing an event that has attendees."* The Hetzner run
decides whether `move_event` stays in that sentence (A5).

### 2.2 Who expands a recurring event (new; R1–R3)

- **A — The server, as today.** A single object the server cannot expand fails the whole
  calendar, and three ordinary shapes do (R1–R3). A per-object fallback is impossible,
  because the server fails the whole REPORT.
- **B — The connector (recommended).** A `calendar-query` with a `time-range` and no
  `expand` returns every object that has an occurrence in the window (R4). ical.js expands
  each one, applying RRULE, RDATE, EXDATE and overrides (`Event.relateException`,
  `iterator()`). An object that cannot be parsed or expanded is skipped and **named** in the
  answer (`skipped: [{ url, reason }]`), instead of failing the calendar (#211.2). The
  iteration is capped per object, 1,000 occurrences inside the window, so a `FREQ=MINUTELY`
  series cannot pin the CPU.

  B is also what makes §2.3 exact. `recurrenceId` comes from the same expansion that the
  write later matches against, rather than from a server's reformatting of it.

### 2.3 How one occurrence is addressed (#206)

`list_events` reports `recurrenceId` for every instance of a series.

- **A — An ISO instant, as today (recommended).** A timed occurrence is reported as UTC
  (`2026-10-08T07:00:00.000Z`), and an all-day one as the date (`2026-10-08`) rather than a
  midnight in whatever zone the process runs in.

  `update_event` and `delete_event` take it back as `recurrence_id`. It is **matched, never
  constructed**: the connector expands the stored series and looks for the occurrence whose
  original start is that instant (or that date). The one it finds carries its RECURRENCE-ID
  in the master's own value type and zone: DATE for an all-day series; `TZID=…` local time
  for a zoned one; UTC for a UTC one; floating for a floating one. No match is refused as
  *not an occurrence of this series*. So the question "which form does the stored DTSTART
  use?" never has to be answered by string conversion.
- **B — The raw stored value** (`20261008T090000;TZID=Europe/Berlin`). It is exact, but
  it is a second date format the model has to carry, and the only one in the whole tool
  surface.

**What the two writes do** (with A):
- **`update_event` with `recurrence_id`** edits that occurrence's override VEVENT if one
  exists. Otherwise it creates one: a copy of the master with RRULE, RDATE and EXDATE
  removed, its VALARMs kept, `RECURRENCE-ID` set, and the patch applied. The override
  gets its own `SEQUENCE`.
- **`delete_event` with `recurrence_id`** adds an `EXDATE` to the master in the master's
  value type and zone, removes an override for that occurrence if there is one, and raises
  the master's `SEQUENCE`. If that was the series' last occurrence, the answer says the
  series now has none, but the object is not deleted.
- **`apply_to_series` stops being required** when `recurrence_id` is given. The two
  together are refused as contradictory.
- **An override-only object** (#211.3, R8) is one occurrence whose series lives elsewhere.
  - `update_event` changes it, with or without `recurrence_id`.
  - `delete_event` deletes the object. On Nextcloud that may send the organizer a decline
    (A6), so the text says so.

### 2.4 What "move the series to 15:00" means (#207)

- **A — New clock time and/or length for every occurrence, each keeping its date
  (recommended).** With `apply_to_series: true`, `start` and `end` describe the new time of
  the occurrence named by `recurrence_id`. Without `recurrence_id` they describe the new time
  of the series' first occurrence. The *difference in wall-clock time* between old and new
  (in the series' own zone, so across DST 09:00 stays 09:00) is applied to the whole
  series:
  - **DTSTART / DTEND:** shifted by it, and the length follows `end` if given.
  - **EXDATE and RDATE:** shifted by the same wall-clock difference, so they keep naming the
    same occurrences (the orphan case in §0.1).
  - **Override RECURRENCE-IDs:** shifted likewise. An override's own DTSTART/DTEND moves too
    **if it still equals its original occurrence time** (it only changed text). An override
    that was rescheduled keeps its explicit time.
  - **UNTIL** (DATE-TIME): shifted by the same difference, so the last occurrence survives
    (the UNTIL case in §0.1). A DATE `UNTIL` and `COUNT` are unchanged.
  - **Refused:** a `start` on a different *date* from the occurrence it names ("the day of a
    series cannot be changed; only its time"); a sub-daily `FREQ`
    (`HOURLY`/`MINUTELY`/`SECONDLY`); and an RRULE with `BYHOUR`/`BYMINUTE`/`BYSECOND`. In
    those cases the time lives in the rule, and shifting DTSTART would contradict it.
- **B — `start` is the new DTSTART, literally.** A model passing the start of a Thursday it
  saw would move the series' anchor to that Thursday and drop every earlier occurrence.
  This is the wrong guess v0.7.2's decision 3 warned about.
- **C — "From this occurrence on"** (split: end the old series with UNTIL, start a new one
  with a new UID). It is common in calendar UIs, but it creates a new event, so on
  Nextcloud it mails new invitations. **Recommended out of v0.7.4**: not one of the twelve.

### 2.5 Time zones (#208, #209)

- **Where the arithmetic comes from.**
  - An object that carries a VTIMEZONE for its TZID: **that VTIMEZONE**. It is how every
    other client reads the event, so the connector reads it the same way.
  - A TZID with no VTIMEZONE that is a valid IANA name, or a path-like TZID ending in one
    (`/mozilla.org/…/Europe/Berlin`): **`Intl`**, exact for every zone (§0.1).
  - Anything else: refused, as #209 says.
  - In memory, the IANA case is handled by inserting a generated VTIMEZONE into the parsed
    object, so ical.js does the recurrence arithmetic correctly. That is local to the
    parse, not `TimezoneService.register`, whose registry is process-wide (R6).
- **A VTIMEZONE the connector has to write.** This happens in only one case: `create_event`
  with a zone, below.
  - **A — Generate it from `Intl` (recommended).** One STANDARD/DAYLIGHT observance per
    actual transition across the event's span, plus one year either side. That is exact
    by construction: `create_event` makes no recurring events, so the span is short.
  - **B — A package** (`timezones-ical-library`). Rejected: measured wrong for Jerusalem
    and Casablanca (§0.1).
  - **C — Write the TZID without a VTIMEZONE**, as Nextcloud and iCloud objects often do.
    Radicale copes (R6). It is an RFC 5545 §3.6.5 violation the connector would be
    *authoring*, not just preserving.
- **An update keeps the event's zone (#208).** A new time for a `TZID=Europe/Berlin` event
  is written as Berlin local time with the same TZID. A UTC event stays UTC, and an all-day
  event stays a date. An object that had no VTIMEZONE is not given one: it goes back the
  way the other client wrote it.
- **Floating stays floating (#209).**
  - `list_events` reports a floating time as clock time with no offset
    (`2026-10-01T09:00:00`) and a new field `timezone: "floating"`. Every event gains that
    `timezone` field: the IANA name, `"UTC"`, or `"floating"`.
  - `update_event` on a floating event **requires times without an offset** and writes them
    floating. A time with an offset is refused with that explanation. Silently dropping the
    offset would move the event by it.
- **`create_event` gets an optional `timezone`** (IANA).
  - **Recommended default:** the calendar's own zone when `list_calendars` reports one
    (Nextcloud sets `calendar-timezone`; Radicale does not, R13), so an event Claude creates
    behaves like one made in the web UI. Otherwise UTC, as today.
  - The answer states which zone was used.

### 2.6 Moving between calendars (#212)

- **A — A new `move_event` tool (recommended):** `calendar_url`, `uid`, `etag`,
  `target_calendar_url`, `apply_to_series` and `account`. Answer: `{ uid, url, etag }` at
  the new place. Moving is not an edit: the content, SEQUENCE and ETag stay the same (R11).
  A separate description can state the one risk moving has (A5) without burying it in
  `update_event`'s text, which is already the longest in the surface. The tool count goes
  from 16 to 17.
- **B — `target_calendar_url` on `update_event`.** Fewer tools, but it gives one call two
  meanings. A move plus a patch in one call would also need two writes and two failure
  points.

**The mechanism** (either option):
1. Look the event up, and **compare the caller's `etag` with the stored one before
   moving.** Radicale ignores `If-Match` on MOVE (R11), so without the explicit comparison
   an event changed on a phone would be moved silently. `If-Match` is still sent, for
   servers that honour it.
2. `MOVE` with `Destination` and `Overwrite: F`, keeping the object's file name.
3. 201/204 is done. `409 no-uid-conflict` is a refusal: *the target calendar already has
   an event with this UID; nothing was moved.* 412 means the name is taken or the event
   changed, and gets the usual re-read refusal.
4. 403, 405, 501, or 502 (a server that refuses cross-collection MOVE) triggers the
   fallback:
   - PUT the object into the target with `If-None-Match: *`, then a guarded DELETE from
     the source.
   - If that DELETE answers 412 (changed meanwhile), the target copy is deleted again and
     the call is refused. The event is in exactly one place either way.
   - If the rollback fails too, the answer names both URLs.
5. A series moves whole. It needs `apply_to_series`, and `recurrence_id` is refused: one
   occurrence cannot live in another calendar.

### 2.7 `find_free_slot` (#213, R14)

- **Filtering: in the connector, not `free-busy-query` (recommended).** Radicale's
  free-busy answer is not the RFC shape (R12), and no server knows which attendee is
  "self". The connector already has every event, so it applies the rules itself:
  - `TRANSP:TRANSPARENT`: free.
  - `STATUS:CANCELLED`: free.
  - The account's own ATTENDEE with `PARTSTAT=DECLINED`: free. "Own" means any `mailto:`
    in `calendar-user-address-set`, or the account's `mail.defaultFrom`.
  - `TENTATIVE`, `NEEDS-ACTION` and everything else: busy.

  A `free-busy-query` path would be a second implementation to test against servers that
  disagree with each other.
- **The working-hours zone.** A new optional `timezone` (IANA). Working hours are applied
  **to every local day in the range** (the R14 fix), DST-correct via `Intl`.
  - **Recommended default:** the calendars' zone when all of them report the same one,
    otherwise UTC.
  - The answer carries `timezone` so the model sees which zone was used. Slots are given
    as ISO times with that zone's offset.

### 2.8 ETags the server hands out oddly (#210)

- **Stripped quotes (#210.2).** If the caller's value without quotes equals the stored
  ETag without quotes, the stored form is used. No decision needed.
- **Weak ETags (#210.3).** `If-Match` uses strong comparison, so a weak ETag can never match
  and every write would loop on 412. A proxy that gzips a response (nginx does this) turns a
  strong ETag weak, so this is a real deployment, not a theoretical one.
  - **A — Compare, then write without `If-Match` (recommended).** When the stored ETag is
    weak, the caller's value is compared with it (ignoring `W/` and quotes) right after the
    lookup, and the write goes without `If-Match`. That keeps the protection #152 is about
    (a change made between `list_events` and `update_event`). It gives up only the
    milliseconds between the lookup and the PUT.
  - **B — Refuse clearly:** *this server's ETags cannot guard a write*. It is safe, and
    unusable on such a server.
- **No ETag at all (#210.1).** The issue proposes `If-Match: *`, but Radicale shows that a
  server can get `*` wrong on PUT (R10).
  - **Recommended:** send `If-Match: *`.
  - On 412, look the event up again. If it is gone, answer with the not-found refusal. If
    it is still there, the server mishandles `*`: retry once with no `If-Match`, and if
    *that* answers 201 (created), delete what was just created and refuse as not found.
  - So an update never leaves a created event behind.
- **Observability (#210.4).** `CalDavClient` gets the tool layer's logger. A failed ETag
  read-back logs one `info` line with the account id and the reason. It stays `null` to
  the caller.

## 3. The tools

### 3.1 `list_events`

- The `calendar-query` has no `expand`, and objects are expanded in the connector (§2.2).
  The `urlFilter` accepts every href except the collection's own (#211.1).
- New fields per event:
  - `timezone`: the IANA name, `"UTC"` or `"floating"`.
  - `transparent`: boolean. It is additive and lets the model see what `find_free_slot`
    counts as free.
- `recurrenceId`: an ISO instant, or `YYYY-MM-DD` for all-day (§2.3).
- A floating event's `start` and `end` carry no offset (§2.5).
- The answer gains `skipped`, a possibly empty list of `{ url, reason }`.

### 3.2 `create_event`

- New **`timezone`** (optional, §2.5).
- New **`notify_attendees`** (boolean, required when `attendees` is non-empty, §2.1).
- ORGANIZER is written when there are attendees.
- `start`/`end` get their own schema: an ISO date-time, or `YYYY-MM-DD` when `all_day`
  (#214).

### 3.3 `update_event`

- `recurrence_id` is live (§2.3).
- `start`/`end` on a series follow §2.4.
- New **`add_attendees`** and **`remove_attendees`**: arrays of email addresses. When
  either is non-empty, `notify_attendees` is required.
- Existing attendees keep `PARTSTAT` and every other parameter.
- Removing an address that is not an attendee is refused. So is adding one that already
  is. Nothing is changed in either case.
- "At least one field" now counts the two attendee lists.

### 3.4 `delete_event`

`recurrence_id` is live (§2.3). The rest is unchanged.

### 3.6 `find_free_slot`

- New **`timezone`** (§2.7), with busy filtering as §2.7 describes.
- `working_hours` is applied to every day.

## 4. Behaviour kept from v0.7.2

- **An update edits the stored object; it never rebuilds it.**
- The caller's ETag guards every write.
- Refusals are `ToolRefusal`s with no `warn` line, and every refusal says what was not
  done.
- A series needs `apply_to_series` for anything that touches every occurrence.

On `~/mail-mcp` with the real Nextcloud account used for v0.7.2. The owner does every step
that needs a real mailbox. **What only Nextcloud can show:**

   controls), first with `notify_attendees: true`, then `false`. Record whether an
   invitation arrives in each case, and whether Nextcloud's UI shows the event as a meeting
   the account organizes.
2. **A2: attendees changed.** On an event the account organizes: add an attendee with
   `true`, add one with `false`, and remove each. Record every mail, and check that the
   remaining attendee's `PARTSTAT` survives. **This decides whether `remove_attendees`
   with `false` is allowed** (§2.1).
3. **A3: one occurrence.** In a weekly series made in Nextcloud's UI (Europe/Berlin), move

   cancelled, the moved Thursday keeps its explicit time, the last occurrence survives, and
   the zone is still Europe/Berlin.
5. **A5: move.** Move an event with an attendee and an alarm between two calendars. It
   appears once, unchanged. Record whether Nextcloud **mails the attendee** (a cancel and
