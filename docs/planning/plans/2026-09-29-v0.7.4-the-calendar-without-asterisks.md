# v0.7.4 — The calendar without asterisks — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every task is TDD: write the named tests, **watch them fail for the stated reason**, then make them pass.

**Status: approved 2026-09-29.** The owner confirmed spec §2 as recommended, so the
"If §2 changes" notes below are moot. Each task pins files, interfaces and the exact test
cases; the code is written test-first while executing, not pasted from here.

**Goal:** Lift every calendar limitation left after v0.7.2 (#203–#214) in one patch, and
fix the four defects that writing the spec found against Radicale (spec §0.1: R1, R2, R3,
R14).

**Architecture:** Four new pure modules take the logic out of `src/caldav-client.ts`,
which is in almost every issue:
- `src/ical-zones.ts` resolves a zone and does the time arithmetic: VTIMEZONE in the
  object, else `Intl` for an IANA name.
- `src/ical-expand.ts` expands a stored object into instances, in the connector instead
  of on the server.
- `src/free-slots.ts` does the busy filtering and per-day working hours.
- `src/ical-edit.ts` grows occurrence, series-shift and attendee edits.

`CalDavClient` keeps the network: the lookup, guarded writes, MOVE with fallback, and the
principal's addresses. `src/tool-refusal.ts` takes `ToolRefusal` out of `tool-errors.ts`
(#214).

**Tech Stack:** TypeScript (ESM, Node ≥ 24, ICU for `Intl`), `tsdav` 2.3.3, `ical.js`
2.2.1, `zod`, `node:test` under `tsx`, Docker Compose (GreenMail + Radicale 3.8.1). **No new
runtime dependency:** spec §2.5 rejects the time-zone package on measured errors.

**Spec:** `docs/planning/specs/2026-09-29-v0.7.4-the-calendar-without-asterisks.md`. Read
§0.1 first. Every shape it lists becomes a test here.

## Global Constraints

- **PR-only onto a protected `main`.** Every `gh` call needs `--repo YannicHock/claude-mail-mcp`.
- **No `Co-Authored-By` trailer and no "Generated with Claude Code" footer.** PR and issue
  bodies go through `--body-file` from a quoted heredoc, never `--body "..."`.
- **CI:** `gh run list --repo … --branch <b>`, then `gh run watch <id> --repo … --exit-status`.
  Never `gh pr checks --watch`: it exits before the image jobs start.
- **Merge style:** a multi-commit branch gets a merge commit `merge: <topic>`; a
  single-commit branch is rebase-merged.
- **Integration suite:** GreenMail 3143/3025/3993 and Radicale 5232 are fixed host ports.
  **Only one checkout runs `npm run test:integration` at a time.** A bind error is
  contention: retry, never edit the compose file, never skip the suite. If Docker is not
  running, start it rather than skipping.
- Every refusal ends by saying what was not done ("Nothing was changed." / "Nothing was
  deleted." / "Nothing was moved.").
- **An update edits the stored object; it never rebuilds it** (v0.7.2 §4.4, kept). Every
  new edit in `ical-edit.ts` gets a preservation test: VALARM, ATTENDEE parameters, X-
  properties, VTIMEZONE and the other overrides all survive.
- `CHANGELOG.md` `## [Unreleased]` in Keep-a-Changelog order: Added, Changed, Fixed. It
  collides on every PR, so resolve by section, not by merge order.
- Hetzner is a playground until v1.0.0. Test there directly, no side instances, and no
  `down -v` unless a step needs a fresh wizard.

## Review Focus

These are the inputs most likely to hurt a real user. Each one has a named test in the
task that owns it:

1. **A DST boundary inside a series move** (Task 5). The series is Berlin 09:00 weekly
   across 2026-10-25, moved to 15:00. Every occurrence must be at 15:00 local, never at
   14:00 or 16:00.
2. **An all-day series' `recurrence_id`** (Task 4). It round-trips as `YYYY-MM-DD` and
   never as a midnight in the process's zone.
3. **The move fallback's rollback** (Task 7). The source DELETE answers 412 after the
   target PUT has succeeded. Afterwards the event exists **once**, in the source.
4. **`notify_attendees: false` on Nextcloud** (Task 6 and acceptance A2). The unit test
   only proves that `SCHEDULE-AGENT=CLIENT` is written. Whether Nextcloud honours it is
   known only after Hetzner, and the tool text must not claim more than A1/A2 showed.
5. **One bad object among many** (Task 2). `list_events` answers with the others plus a
   `skipped` entry, and the UID lookup finds a later exact match past an unparseable
   earlier one.

### Task 2: Expansion in the connector, and a lookup that survives one bad object

**Files:**
- Create `src/tool-refusal.ts`: `ToolRefusal`, moved. `tool-errors.ts` re-exports it, so
  no import breaks (#214).

  `expandObject(ics, window, opts) → { instances: CalendarEvent[]; skipped?: string }`,
  with `MAX_OCCURRENCES_PER_OBJECT = 1000`.
- Create `src/ical-zones.ts` (the reading half):

  - `resolveUnknownTzid(tzid) → string | null`: an IANA name, or the IANA tail of a

  - `findStoredEvent` catches a parse error per object, keeps looking, and applies the
    same `urlFilter`.
  - `parseICalEvents` is deleted, replaced by `expandObject`.
- Modify `src/tools-calendar.ts`: `list_events` returns `skipped`.
- Create `test/unit/ical-expand.test.ts` and `test/unit/ical-zones.test.ts`.
- Modify `test/integration/caldav-calendar.test.ts`.
- Modify `test/helpers/radicale.ts`: one configurable `startCalDavProxy({ weakEtags,
  noEtags, refuseMove, starIfMatchBroken, corruptObject })`. It replaces
  `startEtaglessPutProxy`, whose existing test moves to it.

**Tests (red first). Each fails on today's `main` for the reason given:**
- Integration R1: an all-day weekly series. `list_events` returns three instances with
  `recurrenceId` `2026-10-01`, `2026-10-08`, `2026-10-15`. Today it throws
  `invalid date-time value`.
- Integration R2: a floating weekly series returns two instances with
  `timezone: "floating"` and no offset in `start`. Today: `Collection query failed: 500`.
- Integration R3: an override-only object returns one instance. Today: `400 Bad Request`.
- Integration #211.1: an object stored as `no-extension` is listed and updatable by UID.
  Today it is invisible.
- Integration #211.2 (through the proxy with `corruptObject`):
  - `list_events` answers the other events plus `skipped: [{ url, reason }]`.
  - `update_event` on a UID whose exact match comes after the corrupt object succeeds.
- Integration R5, kept: a TZID series with EXDATE and an override expands exactly as
  Radicale's own expansion did (UTC instants, DST applied).
- Unit (ical-expand):
  - RRULE plus RDATE plus EXDATE plus two overrides, one of them moved out of the window.
  - An infinite `FREQ=MINUTELY` rule stops at the cap and says so in `skipped`.
  - A TZID with no VTIMEZONE yields the same instants as with one (R6).
  - An unknown TZID with no VTIMEZONE is skipped with its reason, not thrown.
- Unit (ical-zones): `Intl` round-trips for Berlin, New York, Sydney, Jerusalem and
  Casablanca across 2026–2030. The DST gap and the overlap follow RFC 5545 §3.3.5:
  - The gap (Berlin 02:30 on 2026-03-29) uses the offset from before the gap, which gives
    `01:30Z`.
  - The overlap (Berlin 02:30 on 2026-10-25) is the *first* occurrence, `00:30Z`. The naive
    two-step `Intl` conversion used while writing the spec returned the second one
    (`01:30Z`), so this test is expected to catch exactly that.

  `resolveUnknownTzid("/mozilla.org/20050126_1/Europe/Berlin")` is `Europe/Berlin`, and for
  `W. Europe Standard Time` it is `null`.

## PR 3: writes that keep their zone, and ETags (#208, #209, #210)

**Branch:** `feat/v0.7.4-zones-and-etags`.

### Task 4a: Zones on write

**Files:**
- `src/ical-zones.ts` (the writing half):
  `vtimezoneFromIntl(tz, fromMs, toMs) → string`. It emits one observance per
  transition, found by a daily scan plus bisection.
- `src/ical-edit.ts`:
  - The time change writes in the event's zone: TZID local time, UTC, DATE or floating.
  - A floating event requires offset-free input.
  - The `unplaced` refusal survives only for an unresolvable TZID.
- `src/caldav-client.ts` and `src/tools-calendar.ts`:
  - `create_event` gets `timezone` (spec §2.5).
  - The default comes from the calendar's `timezone`. Parse the VTIMEZONE text if that is
    what tsdav hands back, or take it as an id (acceptance A7 settles which).

**Tests (red first):**
- A Berlin event moved by `start` alone stays `DTSTART;TZID=Europe/Berlin:…`, keeps its
  VTIMEZONE byte for byte, and keeps its length across the DST change.
- A Berlin event **with no VTIMEZONE**, moved by `start` alone: today this is refused. It
  is now written with the same TZID and still no VTIMEZONE.
- A floating event moved by `start: "2026-10-01T15:00:00"` stays floating. The same call
  with `+02:00` is refused with the explanation.
- A TZID `My Custom Zone` with no VTIMEZONE and one-sided change: still refused.
- `create_event` with `timezone: "Asia/Jerusalem"` writes a VTIMEZONE whose offsets match
  `Intl` at the event's start and end. This is the zone the package got wrong.
- `create_event` with no `timezone` on a calendar with no zone writes UTC, as today.
- Integration: a Berlin event moved through `update_event` expands on Radicale to the
  expected UTC instants.

- Integration: a series with an EXDATE, an override and UNTIL, moved, then checked through
