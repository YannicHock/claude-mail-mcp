> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every task is TDD: write the named tests, **watch them fail for the stated reason**, then make them pass.

**Status: approved 2026-10-18.** The owner took every recommendation except §2.6, which is
configurable (Task 5 says how), and added §2.14 (#247, Task 3b). Where a task still says
"Depends on §2.x", the decision is the recommended one unless this paragraph says otherwise.
The table at the end is kept as a record.

**Issues per task:** Task 1 #162, Task 2 #182, Task 3 #239 #240 #241 #242, Task 3b #247,
Task 4 #27, Task 5 #28, Tasks 6–8 #29.

**Goal:** Threads (#27), incoming attachments (#28), iMIP invitations and answers (#29), the
wizard's default mailbox (#162) and one provider registry (#182), plus the five mail defects
the spec found (§9: F1–F5).

**Architecture:** New pure modules carry the logic, and the network classes stay thin:
- `src/mail-threads.ts`: RFC 5256 `REFERENCES` grouping over header records (pure).
- `src/mail-parts.ts`: the `BODYSTRUCTURE` walk: part ids, which parts are bodies, decoded
  size estimates, the content-block choice for an attachment (pure).
- `src/imip.ts`: build `REQUEST`/`CANCEL`/`REPLY` from a stored object's text, and parse a
  received `text/calendar` part into `get_message`'s `invitation` (pure, ical.js).
- `src/imip-policy.ts`: who is told by whom (spec §2.8): from "server schedules", the
  attendee's parameters and `notify`, which parameters to write and whom the connector
  mails (pure). It is the one place the double-mail rule lives.
- `ImapClient` (`src/imap-client.ts`) gains a narrow `withMailbox(mailbox, fn)` so the thread
  and attachment code can live in their own files (`src/imap-threads.ts`,
  `src/imap-attachments.ts`) without both PRs editing `ImapClient`.
- New tools register from their own files (`src/tools-threads.ts`,
  `src/tools-attachments.ts`, `src/tools-invitations.ts`), called from `src/app.ts` beside
  `registerMailTools`. `src/tools-mail.ts` keeps the nine it has.
- `CalDavClient` gains `schedulesItself()` (the `OPTIONS` detection), cached like
  `ownAddresses()`.

**Against the layout after #234.** v0.7.5's #234 is splitting `src/caldav-client.ts` and
`src/ical-zones.ts`. This plan names modules as #234 describes them: `src/caldav-types.ts`
(the exported interfaces), `src/caldav-move.ts` (the move subsystem), `src/ical-zones-intl.ts`,
`src/ical-vtimezone.ts`, `src/ical-edit-kit.ts` (helpers shared by the editors) and
`test/helpers/caldav-proxy.ts` (the configurable CalDAV proxy, out of
`test/helpers/radicale.ts`). If a name lands differently, follow the responsibility: "the
CalDAV client's network class", "the file holding the CalDAV result types", "the proxy
helper". #234 and #236 are merged and released in v0.7.5, so the iMIP chain is not blocked by
them; the mail PRs (1–5) do not touch those files. After #234, `writeTimeProp` and
`addTimeProp` live in `src/ical-zones.ts`; after #220, `src/net-address.ts` holds
`isPublicIp`/`isLocalIp` and `src/mail-tls.ts` holds `localMailAddress`.

**Tech Stack:** TypeScript (ESM, Node ≥ 24), `imapflow` 2.0.0 (`download`, `bodyStructure`),
`mailparser`, `nodemailer` 10 (its `icalEvent` option builds the iMIP MIME shape, spec M6),

**Spec:** `docs/planning/specs/2026-10-18-v0.8-mail-depth.md`. Read §0.1 first: M1 (GreenMail
has no `THREAD`), M4 (`maxBytes` truncates silently) and M11 (Radicale does not schedule)

## Global Constraints

- **PR-only onto a protected `main`.** Every `gh` call needs `--repo YannicHock/claude-mail-mcp`.
- **No `Co-Authored-By` trailer and no "Generated with Claude Code" footer.** PR and issue
  bodies go through `--body-file` from a quoted heredoc, never `--body "..."`.
- **CI:** `gh run list --repo … --branch <b>`, then `gh run watch <id> --repo … --exit-status`.
  Never `gh pr checks --watch`: it exits before the image jobs start.
- **Merge style:** a multi-commit branch gets a merge commit `merge: <topic>`; a
  single-commit branch is rebase-merged.
- **Integration suite:** GreenMail 3143/3025/3993 and Radicale 5232 are fixed host ports.
  **Only one checkout runs `npm run test:integration` at a time.** A bind error is
  contention: retry, never edit the compose file, never skip the suite. If Docker is not
  running, start it rather than skipping. A probe outside the suite runs its own containers
  on other host ports and stops them afterwards.
- **Real mail.** No test, probe or subagent sends mail to a real address. GreenMail's
  `alice`/`bob` only. Acceptance (Task 10) is the owner's.
- Every refusal ends by saying what was not done. A refusal on an iMIP path says both:
  "Nothing was sent or changed."
- **An update edits the stored object; it never rebuilds it** (kept from v0.7.2). The marker
  parameter and `SCHEDULE-AGENT` are added to an ATTENDEE or ORGANIZER line; every other
  parameter survives, with a preservation test.
- `CHANGELOG.md` `## [Unreleased]` in Keep-a-Changelog order: Added, Changed, Fixed. **It
  collides on every PR**, and in each wave every PR adds to it: resolve by section, not by
  merge order. `test/integration/mcp-protocol.test.ts`' tool list and the README's tool
  table are the other two expected collisions (Tasks 4, 5, 7): each PR adds its own names,
  and the later rebase keeps both.
- Hetzner is a playground until v1.0.0. Test there directly, no side instances other than
  the throwaway Radicale the spec's A7 allows, and no `down -v` except for A11.

## Review Focus

1. **No attendee is mailed twice** (Tasks 6–8). `imip-policy.ts` is tested as a full
   table: server schedules × attendee carries the marker × `notify`. The assertion that
   matters is a negative one: no row both writes an attendee plainly and has the connector
   mail them.
2. **The ceiling is the connector's, not imapflow's** (Task 5). `maxBytes` truncates without
   an error (M4). A test with a part whose `BODYSTRUCTURE` understates its size must be
   refused, not answered with a truncated file.
3. **The Sent copy is the sent message** (Task 3). Same `Message-ID`, same `Date`, `Bcc`
   kept in the copy and **absent from what went over SMTP** (GreenMail's recipient sees no
   `Bcc` header).
4. **A REPLY names only the account** (Task 7). The outgoing `REPLY` holds one ATTENDEE, the
   account's own, never the whole guest list.
5. **The write comes first, the mail second** (Task 8). SMTP down after a successful
   `create_event`: the event exists, the answer says the invitation failed, nothing is
   undone.

### PR 4, Task 4: `list_threads` and `get_thread` (#27)

**Depends on §2.1, §2.2, §2.3.** **Branch:** `feat/v0.8-threads`.

**Files:**
- Create `src/mail-threads.ts` (pure):
  `groupThreads(records: HeaderRecord[]) → Thread[]`, where `HeaderRecord` is `{ mailbox,
  uid, messageId, inReplyTo, references, date, from, to, cc, subject, seen }` and `Thread`
  is `{ messages: HeaderRecord[]; complete: boolean }`. RFC 5256 §4 `REFERENCES` steps 1–4
  (link, find root set, prune empty containers, sort), **without** step 5 (subject merge).
  A `Message-ID` seen twice (INBOX and Sent) is one message; the first record wins, Sent
  last. `normalizedSubject(s)` strips `Re:`, `Fwd:`, `AW:`, `WG:` and `[list]` prefixes for
  display only.
- Create `src/imap-threads.ts`:
  - `fetchHeaderRecords(imap, mailbox, limit)`: through `withMailbox`, one `FETCH` of the
    newest `limit` by sequence with `envelope`, `flags` and `headers: ["references"]`.
    `envelope` carries `messageId` and `inReplyTo`.
  - `threadOf(imap, mailbox, uid, sentFolder)`: the window around the message, grouped, the
    one thread containing it; the bodies of its messages through `getMessage`'s parser,
    text only, capped (spec §2.3).
- Create `src/tools-threads.ts`: `registerThreadTools(server, pool)`, the two tools, with
  `reportingFailures` like the mail tools.
- Modify `src/app.ts`: one line.

**Tests (red first):**

  root); a `References` cycle (no hang, each message once); a message with no threading
